## 5.6 IP：网际协议（IP: Internet Protocol）

### 5.6.1 互联网网络层的主机与路由器功能构成（原页 5b-2）

网络层（Network layer）在协议栈中位于传输层（Transport layer）之下、链路层（Link layer）与物理层（physical layer）之上。主机（host）与路由器（router）在本层运行的协议及其分工如下：

- **传输层**：TCP、UDP。
- **网络层**：
  - **路由协议（Routing protocols）**：其作用是 path selection（路径选择），具体协议为 RIP、OSPF、BGP。
  - **IP 协议（IP protocol）**：其内容为 addressing conventions（编址约定）、datagram format（数据报格式）、packet handling conventions（分组处理约定）。
  - **ICMP 协议（ICMP protocol）**：其内容为 error reporting（差错报告）与 router "signaling"（路由器"信令"）。
- **链路层**与**物理层**：图中仅标示层名。

三者的连接关系是：路由协议的输出指向位于网络层中央的 **routing table（路由表）**，即路由协议负责产生并维护路由表；IP 协议按路由表决定数据报的转发；ICMP 与 IP 协议并列，负责差错报告与路由器之间的信令交互。三个协议都属于网络层。

由此，网络层承担的功能可归纳为：确定地址的表示与分配方式、确定数据报的格式、确定分组的处理规则、选择路径、报告差错。

### 5.6.2 IPv4 数据报格式（IPv4 Datagram Format，原页 5b-3 至 5b-5）

#### 首部的字段布局

IPv4 数据报的首部按"每行 32 bit"的方格结构排布。课件只画出分行结构与字段名，未逐字段标出位宽；下表中的位宽是按 IPv4 标准补出（阅读 5.6.4 节例题必须用到）。

| 行 | 字段 | 位宽 | 含义 |
|----|------|------|------|
| 第 1 行 | ver | 4 bit | IP protocol version number（IP 协议版本号） |
| | head. len | 4 bit | header length (in 4 bytes)（首部长度，单位为 4 字节） |
| | type of service | 8 bit | "type" of data（数据的"类型"） |
| | length | 16 bit | total datagram length (bytes)（数据报总长度，单位字节） |
| 第 2 行 | 16-bit identifier | 16 bit | 用于分片/重组的标识 |
| | flgs（flags） | 3 bit | 标志位，用于分片/重组 |
| | fragment offset | 13 bit | 分片偏移量，用于分片/重组 |
| 第 3 行 | time to live | 8 bit | max number remaining hops，decremented at each router（最多还可经过的跳数，每经过一个路由器减 1） |
| | upper layer | 8 bit | upper layer protocol to deliver payload to（把有效载荷交付给哪个上层协议） |
| | header checksum | 16 bit | 首部校验和 |
| 第 4 行 | 32 bit source IP address | 32 bit | 源 IP 地址 |
| 第 5 行 | 32 bit destination IP address | 32 bit | 目的 IP 地址 |
| 第 6 行 | options (if any) | 可变 | 例如 timestamp、record route taken、specify list of routers to visit（时间戳、记录所经过的路由、指定要访问的路由器列表） |
| 之后 | data | 可变 | variable length, typically a TCP or UDP segment（可变长度，通常是 TCP 或 UDP 报文段） |

首部固定部分为 5 行 × 32 bit = 20 字节（对应 head. len = 5）；options 只有在选项存在时才占据空间。课件在同一页给出首部开销的结论：20 bytes of TCP（TCP 首部 20 字节）＋ 20 bytes of IP（IP 首部 20 字节）＝ 40 bytes + app layer overhead。即一个携带 TCP 报文段的 IP 数据报，在应用层数据之外至少要付出 40 字节固定开销。

#### 上层协议字段（upper layer / protocol field，原页 5b-4）

第 3 行中的 **upper layer** 字段（标准中的 protocol 字段）指明数据部分应交付给哪一个上层协议。课件给出的取值如下：

| 协议 | 字段取值 |
|------|----------|
| ICMP | 1 |
| IGMP | 课件未标出取值（标准值为 2，此处为补充说明） |
| TCP | 6 |
| UDP | 17 |
| OSPF | 89 |

同一字段既可以取值指向传输层协议（TCP、UDP），也可以取值指向网络层自身的控制协议（ICMP、IGMP、OSPF）。

#### 首部校验和（原页 5b-5）

课件本页只有一个标题"Header checksum (To be discussed in Transport Layer)"，正文区域为空，即：**首部校验和的计算方法在本课件中被安排到传输层（Transport Layer）部分讲解**，此处不展开，照课件原样记录。

### 5.6.3 IP 分片与重组（IP Fragmentation & Reassembly，原页 5b-6 至 5b-8）

#### 分片的原因：MTU 限制（原页 5b-6）

课件给出的前提：

- network links have MTU (max. transfer size) — largest possible link-level frame。每条网络链路都有一个 **MTU（最大传输单元，Maximum Transfer Size）**，指该链路所能承载的最大的链路层帧。
- different link types, different MTUs：不同链路类型的 MTU 不同。
- large IP datagram divided ("fragmented") within net：大的 IP 数据报在网络内部被划分（"分片"）。
  - one datagram becomes several datagrams：一个数据报变成若干个数据报；
  - "reassembled" only at final destination：只在最终目的端进行"重组"；
  - IP header bits used to identify, order related fragments：用 IP 首部中的若干比特来标识、排序相互关联的各分片。

课件本页图示的转发情形为：一台主机发出一个大的数据报（in: one large datagram），经过网络中某路由器时被分成 3 个较小的数据报（out: 3 smaller datagrams），这 3 个分片分别沿路径转发，到达目的主机所在网络后才由目的主机重组（reassembly）为一个完整数据报。

由此可确定责任划分：**分片由网络中的路由器执行，重组只在最终目的主机执行，中间路由器不重组。**

#### 分片过程与偏移量计算（原页 5b-7）

课件用一个数值例子给出分片边界与偏移量。网际协议首部为 20 字节，数据部分为 3980 字节，数据字节编号为 byte 0 至 byte 3979；原始数据报整体的 offset 标注为 $0/8=0$。分片边界按字节标出为 byte 0、1480、2960、3979。

| 分片 | 携带的数据字节编号 | 偏移量计算 | fragment offset 字段值 |
|------|--------------------|------------|------------------------|
| fragment 1 | byte 0 – byte 1479（共 1480 字节） | $0/8$ | 0 |
| fragment 2 | byte 1480 – byte 2959（共 1480 字节） | $1480/8$ | 185 |
| fragment 3 | byte 2960 – byte 3979（共 1020 字节） | $2960/8$ | 370 |

每个分片都带有自己的首部（header 1、header 2、header 3）。**偏移量的单位是 8 字节**，所以字节位置要除以 8 之后才写入 fragment offset 字段：$0/8=0$，$1480/8=185$，$2960/8=370$。也正因为偏移量以 8 字节为单位，除最后一片外，每片的数据长度必须是 8 的整数倍。

数据长度验算：$1480+1480+1020=3980$ 字节，与原始数据字段的 3980 字节一致。

#### 分片首部字段的取值（原页 5b-8）

同一个例子的首部字段取值前后对照如下：一个大（original）数据报的 length=4000、ID=x、fragflag=0、offset=0；它变成 3 个小数据报后各字段为

| 数据报 | length | ID | fragflag | offset |
|--------|--------|----|----------|--------|
| 原始大数据报 | 4000 | x | 0 | 0 |
| 分片 1 | 1500 | x | 1 | 0 |
| 分片 2 | 1500 | x | 1 | 185 |
| 分片 3 | 1040 | x | 0 | 370 |

要点：

1. **length** 是首部加数据的**总长度**（单位字节）：$4000=20+3980$；前两片 $1500=20+1480$；最后一片 $1040=20+1020$。
2. **ID（16-bit identifier）** 三个分片都等于 x，即同一原始数据报的所有分片共用同一个标识值，用于在目的端判定哪些分片属于同一个原始数据报。
3. **fragflag**：前两片为 1，最后一片为 0，表示"后面还有分片"（标准中对应 MF，More Fragments 位，此对应关系为补充说明）：1 表示其后的分片还属于同一个原始数据报，0 表示这是最后一个分片。
4. **offset**：0、185、370，即数据在原始数据报数据字段中的位置除以 8。

数值一致性验算：$1500+1500+1040=4040$ 字节，而原始数据报为 4000 字节，差值 $4040-4000=40$ 字节，恰好等于分片 2 与分片 3 各自新增的一个 IP 首部（各 20 字节），即每个分片除第一片外都要额外付出 20 字节首部开销。

### 5.6.4 例题：IPv4 数据报首部的逐字段解析（原页 5b-9）

**题干**：Now assume a IP datagram is captured. The first 20 bytes are as follows（假定捕获到一个 IP 数据报，其前 20 个字节如下）：

```
0x45 0x00 0x00 0x3C 0x1A 0x37 0x00
0x00 0x80 0x01 0x6E 0x31 0xC0 0xA8
0x01 0xD4 0xD3 0x9B 0x1C 0x41
```

Please try to analyze the value and meaning of each field in the IP datagram header.（试分析 IP 数据报首部中每个字段的取值与含义。）

课件只给出题干，未给出解答，以下按字段顺序逐字节解析并复算。

**解**：

第 1 步：把 20 个字节按顺序编号（从 0 开始）并两两组成 16 比特字：

| 字节序号 | 十六进制 | 16 比特字 |
|----------|----------|-----------|
| 0 | 0x45 | 0x4500 |
| 1 | 0x00 | （与上一字节同字） |
| 2 | 0x00 | 0x003C |
| 3 | 0x3C | （与上一字节同字） |
| 4 | 0x1A | 0x1A37 |
| 5 | 0x37 | （与上一字节同字） |
| 6 | 0x00 | 0x0000 |
| 7 | 0x00 | （与上一字节同字） |
| 8 | 0x80 | 0x8001 |
| 9 | 0x01 | （与上一字节同字） |
| 10 | 0x6E | 0x6E31 |
| 11 | 0x31 | （与上一字节同字） |
| 12 | 0xC0 | 0xC0A8 |
| 13 | 0xA8 | （与上一字节同字） |
| 14 | 0x01 | 0x01D4 |
| 15 | 0xD4 | （与上一字节同字） |
| 16 | 0xD3 | 0xD39B |
| 17 | 0x9B | （与上一字节同字） |
| 18 | 0x1C | 0x1C41 |
| 19 | 0x41 | （与上一字节同字） |

第 2 步：第 0 字节 0x45 = 0100 0101B，高 4 位 ver = 0100B = 4，即**版本号 = 4（IPv4）**；低 4 位 head. len = 0101B = 5，单位是 4 字节，故**首部长度 = 5 × 4 = 20 字节**，说明没有 options，数据从第 20 字节开始。

第 3 步：第 1 字节 0x00，即 type of service = 0x00，8 位全 0，**服务类型字段取值为 0**。

第 4 步：第 2、3 字节组成 0x003C，作为 length（总长度）：$0\text{x}3\text{C}=3\times16+12=60$，即**数据报总长度 = 60 字节**。其中首部占 20 字节，故**数据部分长度 = 60 − 20 = 40 字节**。

第 5 步：第 4、5 字节 0x1A37 是 16-bit identifier（标识）：$1\times4096+10\times256+3\times16+7=4096+2560+48+7=6711$，即**标识 = 6711**。

第 6 步：第 6 字节 0x00 的高 3 位为 flags = 000B，即保留位、DF（Don't Fragment）位、MF（More Fragments）位全为 0，说明**允许分片且本数据报不是分片，其后也没有属于同一数据报的分片**。

第 7 步：第 6 字节的低 5 位与第 7 字节 0x00 共同构成 13 位的 fragment offset：0x0000，即**片偏移 = 0**，与第 6 步结论一致。

第 8 步：第 8 字节 0x80，即 time to live = $8\times16=128$，**TTL = 128**，表示该数据报最多还能经过 128 跳，每经过一个路由器减 1。

第 9 步：第 9 字节 0x01，即 upper layer（协议）字段 = 1，上层协议为 **ICMP**，即该数据报的数据部分要交付给 ICMP 处理。

第 10 步：第 10、11 字节 0x6E31，即 header checksum = $6\times4096+14\times256+3\times16+1=24576+3584+48+1=28209$，**首部校验和 = 0x6E31 = 28209**（校验复算见第 13 步）。

第 11 步：第 12–15 字节 0xC0 0xA8 0x01 0xD4 为源 IP 地址：$0\text{xC}0=192$，$0\text{xA}8=168$，$0\text{x}01=1$，$0\text{xD}4=13\times16+4=212$，**源 IP 地址 = 192.168.1.212**。

第 12 步：第 16–19 字节 0xD3 0x9B 0x1C 0x41 为目的 IP 地址：$0\text{xD}3=13\times16+3=211$，$0\text{x}9\text{B}=9\times16+11=155$，$0\text{x}1\text{C}=16+12=28$，$0\text{x}41=4\times16+1=65$，**目的 IP 地址 = 211.155.28.65**。

第 13 步：用原始数据校验首部校验和。把 10 个 16 比特字（含校验和字段本身）按反码求和：

| 加数 | 十进制 | 累加结果（十进制） | 累加结果（十六进制） |
|------|--------|--------------------|----------------------|
| 0x4500 | 17664 | 17664 | 0x4500 |
| 0x003C | 60 | 17724 | 0x453C |
| 0x1A37 | 6711 | 24435 | 0x5F73 |
| 0x0000 | 0 | 24435 | 0x5F73 |
| 0x8001 | 32769 | 57204 | 0xDF74 |
| 0x6E31 | 28209 | 85413 | 0x14DA5 |
| 0xC0A8 | 49320 | 134733 | 0x20E4D |
| 0x01D4 | 468 | 135201 | 0x21021 |
| 0xD39B | 54171 | 189372 | 0x2E3BC |
| 0x1C41 | 7233 | 196605 | 0x2FFFD |

累加和 $196605=\text{0x}2\text{FFFD}$，超过 16 位，把溢出的高位折返相加：$0\text{x}0002+0\text{xFFFD}=0\text{xFFFF}$。再按位取反：$\overline{\text{0xFFFF}}=\text{0x0000}$，与"校验和正确时反码求和结果应为全 1、取反后为 0"一致，故**首部校验和 0x6E31 正确，首部未发生传输错误**。

第 14 步：把结果回代题干原始数据核对：首部长度 20 字节 + 数据 40 字节 = 60 字节 = 0x003C，与第 4 步的总长度字段相符；第 9 步得协议为 ICMP 且数据长度 40 字节；第 6、7 步得 DF=0、MF=0、偏移 0，说明本数据报可被后续链路分片且当前未被分片，16-bit identifier = 6711 在同源同目的的数据报中唯一标识该数据报。

**答案**：

| 字段 | 取值 | 含义 |
|------|------|------|
| ver | 4 | IP 协议版本 4 |
| head. len | 5（×4 = 20 字节） | 首部长度 20 字节，无选项 |
| type of service | 0x00 | 服务类型 0 |
| length | 0x003C = 60 字节 | 数据报总长（数据部分 40 字节） |
| 16-bit identifier | 0x1A37 = 6711 | 数据报标识 |
| flags | 0（DF=0，MF=0） | 未分片，允许分片 |
| fragment offset | 0 | 第一个分片/完整数据报 |
| time to live | 0x80 = 128 | 剩余跳数上限 128 |
| upper layer | 0x01 = 1 | 上层协议为 ICMP |
| header checksum | 0x6E31 = 28209 | 首部校验和，校验通过 |
| source IP address | 192.168.1.212 | 源地址（属保留私有地址段） |
| destination IP address | 211.155.28.65 | 目的地址 |

### 5.6.5 IPv4 编址（IPv4 Addressing，原页 5b-10 至 5b-30）

#### 地址与接口（原页 5b-10、5b-11）

- **IP address（IP 地址）**：32-bit identifier for host, router interface，即用于主机、路由器接口的 32 比特标识符。
- **interface（接口）**：connection between host/router and physical link，即主机/路由器与物理链路之间的连接。
  - router's typically have multiple interfaces：路由器通常有多个接口；
  - host typically has one or two interfaces (e.g., wired Ethernet, wireless 802.11)：主机通常有一个或两个接口（例如有线以太网接口、无线 802.11 接口）。
- **IP addresses associated with each interface**：IP 地址与每一个接口相关联，而不是与"一台机器"整体相关联。

课件图示的拓扑（三个网络通过一个路由器互连）与地址分配如下：

| 位置 | 接口地址 |
|------|----------|
| 左侧网络的三台主机 | 223.1.1.1、223.1.1.2、223.1.1.3 |
| 路由器与左侧网络相连的接口 | 223.1.1.4 |
| 路由器与右侧网络相连的接口 | 223.1.2.9 |
| 路由器与下方网络相连的接口 | 223.1.3.27 |
| 右侧网络的两台主机 | 223.1.2.1、223.1.2.2 |
| 下方网络的两台主机 | 223.1.3.1、223.1.3.2 |

同一图给出的点分十进制（dotted-decimal）到二进制的展开为

$$223.1.1.1 = 11011111\;00000001\;00000001\;00000001$$

其中 $223=11011111\text{B}$，$1=00000001\text{B}$，即点分十进制表示法就是把 32 比特按 8 比特一组、每组用十进制写出并用点分隔。

关于接口实际如何连接：有线以太网接口由以太网交换机（Ethernet switches）连接，无线 WiFi 接口由 WiFi 基站（WiFi base station）连接；在讨论编址时暂不关心接口之间（无中间路由器）具体如何连接（For now: don't need to worry about how one interface is connected to another）。

#### 子网与子网的判定（原页 5b-12 至 5b-14）

- **IP 地址的两部分**：subnet part — high order bits（**子网部分，高位比特**）；host part — low order bits（**主机部分，低位比特**）。
- **subnet（子网）**：device interfaces with same subnet part of IP address（具有相同子网部分的 IP 地址的设备接口）；can physically reach each other without intervening router（可以不经由中间路由器而彼此物理可达）。上述三网络拓扑 "consisting of 3 subnets"，即由 3 个子网构成。

**判定方法（recipe）**：to determine the subnets, detach each interface from its host or router, creating islands of isolated networks；each isolated network is called a subnet。即把每个接口从它所属的主机或路由器上"摘除"，得到若干个彼此孤立的网络，每一个孤立的网络就是一个子网。

按该 recipe 对上述拓扑操作的结果：左侧网络为 $223.1.1.0/24$，右侧网络为 $223.1.2.0/24$，下方网络为 $223.1.3.0/24$，subnet mask 为 /24。此处的 /24 表示前 24 位为子网部分、后 8 位为主机部分。以 $223.1.1.0/24$ 为例，它包含主机接口 223.1.1.1、223.1.1.2、223.1.1.3 和路由器接口 223.1.1.4。

#### 分类编址（class-full addressing，原页 5b-15）

**class-full addressing（分类编址）**把 32 比特地址空间按下述方式划分：

| class（类） | 首部比特 | 网络号部分 | 主机号部分 | 地址范围 |
|-------------|----------|------------|------------|----------|
| A | 0 | 7 bit（network） | 24 bit（host） | 1.0.0.0 to 127.255.255.255 |
| B | 10 | 14 bit（network） | 16 bit（host） | 128.0.0.0 to 191.255.255.255 |
| C | 110 | 21 bit（network） | 8 bit（host） | 192.0.0.0 to 223.255.255.255 |
| D | 1110 | 28 bit（multicast address） | — | 224.0.0.0 to 239.255.255.255 |

"首部比特"一列为区分类别的前缀位：A 类以 0 开头、B 类以 10 开头、C 类以 110 开头、D 类以 1110 开头；D 类没有网络号/主机号的划分，其前缀之后的部分整体为多播地址（multicast address）。分类编址下，从地址的第一个字节即可判定类别，从而确定哪几位是网络号、哪几位是主机号。（各字段位宽为按前缀位推出的标准数值，课件未直接标出。）

课件用一张中文表列出网络号与主机号取特殊值时的地址类型与用途：

| 网络号 | 主机号 | 地址类型 | 用途 |
|--------|--------|----------|------|
| 全0 | 全0 | 本机 | 启动时使用 |
| 网络ID | 全0 | 网络 | 标识一个网络 |
| 网络ID | 全1 | 直接广播 | 在指定网上广播 |
| 全1 | 全1 | 有限广播 | 在本地网上广播 |

#### 分类编址的缺陷与子网划分（原页 5b-17）

分类编址存在两个问题：

- inefficient use of address space, address space exhaustion：地址空间使用效率低，导致地址空间耗尽；
- 例如：class B net allocated enough addresses for 65K hosts, even if only 2K hosts in that network。一个 B 类网络被分配了足以容纳 65K 台主机的地址（B 类主机号 16 位，$2^{16}=65536$），即使该网络中只有 2K 台主机，余下的地址也无法被其他网络使用。

应对办法是 **Subnetting and subnet mask（子网划分与子网掩码）**。课件给出一个比特划分示例：地址 200.23.16.64/27，其二进制为

$$11001000\;00010111\;00010000\;01000000$$

其中 network part 覆盖前 24 位（$11001000\;00010111\;00010000$），其后的 subnet part 为接下来的 3 位（$010$），host part 为最后 5 位（$00000$）。按此划分复算（补充计算，课件未展开）：前缀长度 /27 表示前 27 位为网络号与子网号之和，故子网号占 $27-24=3$ 位，主机号占 $32-27=5$ 位；该地址所在子网的网络地址是把主机号 5 位置 0，即 200.23.16.64；主机号 5 位取值 00001–11110 可分配给主机，共 $2^{5}-2=30$ 个可用主机地址（除去主机号全 0 的网络地址与全 1 的广播地址），可用范围为 200.23.16.65 – 200.23.16.94，广播地址为 200.23.16.95。

课件在同一页给出点分十进制表示法的示例：193.32.216.9，其二进制为 $11000001\;00100000\;11011000\;00001001$。

#### 子网划分示例：B 类网络 145.13.0.0（原页 5b-18、5b-19）

不使用子网时，一个 B 类网络 145.13.0.0 的拓扑为：

- 中间是一个标注 "network 145.13.0.0" 的网络，其中主机地址为：145.13.3.10、145.13.3.11、145.13.3.101、145.13.7.34、145.13.7.35、145.13.7.56、145.13.21.23、145.13.21.9、145.13.21.8（图中另有两处省略号，表示还有未列出的主机）。
- 网络外接三个路由器 $R_1$、$R_2$、$R_3$：$R_1$ 直接与该网络相连，$R_2$ 与 $R_3$ 通过链路连到 $R_1$。
- $R_2$ 旁的标注为 "My network ID is 145.13.0.0"；$R_1$ 旁的标注为 "All packets to 145.13.0.0 can reach this router"。
- $R_1$ 与 $R_2$、$R_3$ 之间用箭头表示路由通告/可达性关系。

这说明：在**不使用子网**时，整个 145.13.0.0 是一个网络，所有目的地址以 145.13 开头的数据报都被引向 $R_1$，路由器只需要知道"网络 145.13.0.0"这一条路由信息。

同一张图的下一帧标题为 "A network for others, the class B with 3 subnet"（该网络的其余部分：带 3 个子网的 B 类网络），与上一帧构成同一动画的前后页。在该帧中，图形标注与上一帧逐项相同（地址、路由器标注、箭头均一致），**未出现新增的子网划分标注线或各子网的地址范围**，因此三个子网的具体划分（子网掩码、各子网地址）在该页未印出。按图中主机地址的分布可作出的推断（课件未明示，仅供参考）：主机地址按第三个字节分为三组——145.13.3.x、145.13.7.x、145.13.21.x，与标题中的 "3 subnet" 相呼应，即该 B 类网络被划分为 3 个子网，每个子网内的主机地址第三个字节取值相同。

#### 子网掩码（Subnet mask，原页 5b-20）

子网掩码的作用可用四级对照说明：

1. **两级 IP 地址（Two level IP address）**：地址分成 Network ID（网络号）与 Host ID（主机号）两部分。
2. **三级 IP 地址（Three level IP address）**：地址分成 Network ID、Subnet ID（子网号）、Host ID 三部分，即在原网络号之后插入子网号。
3. **子网掩码（Subnet mask）**：

$$11111111\;11111111\;11111111\;00000000$$

即前 24 位全为 1、后 8 位全为 0。

4. **子网的网络号（Network ID of the subnet）**：将三级 IP 地址与子网掩码做 **AND operation（按位与运算）**，得到的结果是 Network ID + Subnet ID，即**子网的网络号**；主机号部分（对应掩码中为 0 的位）被置 0 而不再保留。

由此可归纳子网掩码的构成规则：掩码是一个 32 比特数，其中**连续的 1 对应网络号与子网号，连续的 0 对应主机号**；1 的位数就是"网络号 + 子网号"的长度。上例掩码的 1 有 24 位，等价于点分十进制 255.255.255.0。

按图示做法复算一例（补充计算，用前述 145.13.x.x 的地址数据）：取地址 145.13.3.10 与掩码 255.255.255.0 按位与——

$$
\begin{aligned}
&\ \ 145.13.3.10 \quad = 10010001\;00001101\;00000011\;00001010\\
&\ \ 255.255.255.0 = 11111111\;11111111\;11111111\;00000000\\
&\ \ \text{AND} \quad\quad = 10010001\;00001101\;00000011\;00000000 = 145.13.3.0
\end{aligned}
$$

结果为 145.13.3.0，即该地址所属子网的网络号；同理 145.13.7.34 与掩码 255.255.255.0 按位与得 145.13.7.0，145.13.21.23 得 145.13.21.0。三个子网的网络号互不相同（145.13.3.0、145.13.7.0、145.13.21.0），与 "3 个子网" 一致。路由器在转发时用"目的 IP 地址 AND 子网掩码"即可得到目的子网的网络号，再据此查表选择下一跳；使用子网划分后，同一个 B 类网络 145.13.0.0 内部的三个子网在网络外部仍可只对外通告"145.13.0.0"这一条汇总路由，而在网络内部按子网号区分转发。

#### CIDR：无类别域间路由（原页 5b-21）

**CIDR（Classless InterDomain Routing，无类别域间路由）**的要点如下：

- 地址仍为两级结构，只包含两部分：网络部分与主机部分。
- 网络部分的长度是任意的（arbitrary length），不再限定为类别地址（A/B/C 类）所规定的 8、16、24 位。
- 地址书写格式为 `a.b.c.d/x`，其中 `x` 表示网络部分所占的比特数。`a.b.c.d` 为点分十进制表示的 32 位地址，`x` 为 0 到 32 之间的整数。
- 网络部分通常称为前缀（prefix）。

课件给出的示例为 32 位地址 `11001000 00010111 00010000 00000000`，前缀长度为 23，即前 23 位属于网络部分（`11001000 00010111 0001000`），其余 9 位属于主机部分，写成 CIDR 形式为

$$200.23.16.0/23$$

其逐字节对应关系为：$200=11001000_2$，$23=00010111_2$，$16=00010000_2$，$0=00000000_2$；拼接后取前 23 位作前缀，末 9 位（第三个字节的最后 1 位加上整个第四个字节的 8 位）为主机位。

CIDR 与类别地址的差别在于：类别地址中网络号长度由地址首字节的高位比特固定决定（A 类 8 位、B 类 16 位、C 类 24 位），而 CIDR 中网络号长度由 `/x` 中的 `x` 显式给出，长度为任意值。这使地址块可按实际需要的规模切分，缓解了前述"地址空间利用率低、地址空间耗尽"的问题。

对一个前缀长度为 $x$ 的地址块，主机位数为 $32-x$，共包含 $2^{32-x}$ 个地址。其中两个地址有特殊含义：主机位全 0 的地址为该地址块的网络地址，主机位全 1 的地址为该地址块的广播地址（定向广播地址）。因此该地址块中可用于分配给主机接口的地址数为 $2^{32-x}-2$。

#### 主机如何获得 IP 地址与 DHCP（原页 5b-23 至 5b-25）

主机（Hosts）获得 IP 地址有两种方式：

1. 由系统管理员在文件中硬编码（hard-coded by system admin in a file），即静态配置。
2. **DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）**：允许主机在接入网络时从网络服务器动态地获得其 IP 地址。

DHCP 的四项性质：

- "即插即用"（"plug-and-play"）。
- 可以续租（renew its lease）正在使用的地址。
- 允许地址复用：主机只在其处于连接/开机状态期间持有该地址。
- 支持希望接入网络的移动用户。

其中 lease 表示地址按租约发放，租约有一个有效期（下一页给出租约的 lifetime 参数）。租约到期而未续租时，该地址可被重新分配，这是地址复用的实现前提。

DHCP 场景的拓扑为：一个路由器把三个子网互联，另有一台 DHCP 服务器接在中间子网。图中地址标注如下：

- 三个子网的地址块：$223.1.1.0/24$、$223.1.2.0/24$、$223.1.3.0/24$。
- 左侧子网 $223.1.1.0/24$ 上的接口地址：$223.1.1.1$、$223.1.1.2$、$223.1.1.3$，以及路由器在该子网的接口 $223.1.1.4$。
- 中间子网 $223.1.2.0/24$ 上的接口地址：$223.1.2.9$（路由器接口）、$223.1.2.2$、$223.1.2.1$；DHCP 服务器接入该子网（其地址 $223.1.2.5$ 由下一页明确给出）。
- 下方子网 $223.1.3.0/24$ 上的接口地址：$223.1.3.1$、$223.1.3.2$，以及路由器在该子网的接口 $223.1.3.27$。
- 图中新接入的主机标注为 "arriving DHCP client needs address in this network"（新到达的 DHCP 客户，在本网络中需要一个地址）。

即 DHCP 服务器位于其中一个子网，但可以为多个子网中接入的主机分配地址（客户与服务器不一定在同一子网）。

一次完整的地址获取过程由四个报文组成，DHCP 服务器地址为 $223.1.2.5$：

| 报文 | 源地址:端口 | 目的地址:端口 | yiaddr | 事务 ID | lifetime | 图中广播文字 |
|------|-------------|---------------|--------|---------|----------|--------------|
| DHCP discover | 0.0.0.0, 68 | 255.255.255.255, 67 | 0.0.0.0 | 654 | — | Broadcast: is there a DHCP server out there? |
| DHCP offer | 223.1.2.5, 67 | 255.255.255.255, 68 | 223.1.2.4 | 654 | 3600 secs | Broadcast: I'm a DHCP server! Here's an IP address you can use |
| DHCP request | 0.0.0.0, 68 | 255.255.255.255, 67 | 223.1.2.4 | 655 | 3600 secs | Broadcast: OK. I'll take that IP address! |
| DHCP ACK | 223.1.2.5, 67 | 255.255.255.255, 68 | 223.1.2.4 | 655 | 3600 secs | Broadcast: OK. You've got that IP address! |

逐项说明：

- 端口号：服务器使用 UDP 端口 67，客户使用 UDP 端口 68。discover 与 request 由客户发往服务器，故目的端口为 67、源端口为 68；offer 与 ACK 由服务器发往客户，故源端口为 67、目的端口为 68。
- 源地址：discover 与 request 由尚无 IP 地址的客户发出，源地址填 $0.0.0.0$；offer 与 ACK 由服务器发出，源地址为其自身地址 $223.1.2.5$。
- 目的地址：四个报文的目的地址均为 $255.255.255.255$（受限广播地址）。原因是客户此时还不知道服务器地址，而服务器在客户确认租用之前也不知道客户的单播地址。
- yiaddr（your IP address）：服务器分配给客户的 IP 地址。discover 阶段客户尚未被告知，填 $0.0.0.0$；offer 起填为 $223.1.2.4$，属于中间子网 $223.1.2.0/24$，与该子网前缀一致。
- 事务 ID（transaction ID）：discover 与 offer 同为 654，request 与 ACK 同为 655。请求与对应的应答使用相同事务 ID，用于把应答与请求配对。
- lifetime：租约时长，offer、request、ACK 三个报文中均为 3600 secs（1 小时）。

分步叙述：

1. 客户广播 DHCP discover（源 0.0.0.0:68，目的 255.255.255.255:67，事务 ID 654），询问网络中是否存在 DHCP 服务器。
2. 服务器 223.1.2.5 广播 DHCP offer（源 223.1.2.5:67，目的 255.255.255.255:68，事务 ID 654），告知自己是 DHCP 服务器，并提供一个可用地址 223.1.2.4，租约 3600 秒。
3. 客户广播 DHCP request（源 0.0.0.0:68，目的 255.255.255.255:67，事务 ID 655，yiaddr 223.1.2.4），表示接受该地址。
4. 服务器广播 DHCP ACK（源 223.1.2.5:67，目的 255.255.255.255:68，事务 ID 655，yiaddr 223.1.2.4），确认客户已获得该地址。

offer 与 request 之间的作用是把"服务器提出候选地址"与"客户确认选用该地址"分开：客户可能同时收到多个服务器的 offer，需要用 request 明确指出选用的地址（此处为 223.1.2.4）。获得 ACK 后，客户才正式持有该地址及其租约。

#### 网络如何获得地址块：ISP 分配与层次化编址（原页 5b-26 至 5b-29）

网络从 ISP 的地址空间中分得一部分（get allocated portion of ISP's address space）。示例中 ISP 持有地址块 $200.23.16.0/20$，它把该块按 /23 切分给若干组织：

| 机构 | 二进制 | 地址块 |
|------|--------|--------|
| ISP's block | 11001000  00010111  00010000  00000000 | 200.23.16.0/20 |
| Organization 0 | 11001000  00010111  00010000  00000000 | 200.23.16.0/23 |
| Organization 1 | 11001000  00010111  00010010  00000000 | 200.23.18.0/23 |
| Organization 2 | 11001000  00010111  00010100  00000000 | 200.23.20.0/23 |
| … | … | … |
| Organization 7 | 11001000  00010111  00011110  00000000 | 200.23.30.0/23 |

（表中"…"两行是课件原有的省略行，表示 Organization 3 至 Organization 6 的地址块，课件未逐行列出数值。）

逐行核对第三个字节的二进制与十进制：16 $=00010000$；18 $=00010010$；20 $=00010100$；30 $=00011110$。这四个 /23 地址块的前 20 位都相同：前两个字节相同，第三个字节的前 4 位均为 `0001`。因此它们全部落在 ISP 的 $200.23.16.0/20$ 之内，且 /23 把每个组织限制在第三个字节的后 3 位加第四个字节（共 9 位主机位）范围内，相邻组织的第三字节相差 2（16→18→20→…→30），彼此不重叠。ISP 的 /20 共含 $2^{12}=4096$ 个地址，按 /23 每块 512 个地址切分，最多可切出 $4096/512=8$ 块，正好对应 Organization 0 ~ Organization 7 共 8 个组织。

层次化编址（hierarchical addressing）使路由信息能够被高效地通告（efficient advertisement of routing information）。图中给出两个通告：

- Fly-By-Night-ISP 向 Internet 通告："Send me anything with addresses beginning 200.23.16.0/20"。它下挂 Organization 0（200.23.16.0/23）、Organization 1（200.23.18.0/23）、Organization 2（200.23.20.0/23）、……、Organization 7（200.23.30.0/23）。
- ISPs-R-Us 向 Internet 通告："Send me anything with addresses beginning 199.31.0.0/16"。

关键在于：Fly-By-Night-ISP 的下层组织使用的是同一 /20 前缀内的连续 /23 子块，所以这个 ISP 只需对外通告一条 /20 前缀，而不必为 8 个组织分别通告 8 条 /23 前缀。由多个较短前缀合并为一条较长覆盖前缀的做法称为**路由聚合（route aggregation）**。无此聚合时，Internet 中其他路由器需要保存并处理 8 条独立路由；有聚合时只需 1 条。

课件进一步给出一种情形：ISPs-R-Us 拥有通往 Organization 1 的一条更具体的路由（more specific route）。此时：

- Fly-By-Night-ISP 仍然通告 $200.23.16.0/20$，但其下挂的不再是 Organization 1，而是 Organization 0、Organization 2、……、Organization 7。
- Organization 1（200.23.18.0/23）改挂到 ISPs-R-Us 之下。
- ISPs-R-Us 向 Internet 通告："Send me anything with addresses beginning 199.31.0.0/16 or 200.23.18.0/23"，即同时通告原有的 /16 前缀和这条新增的 /23 前缀。

该情形的含义是：Organization 1 的地址块 $200.23.18.0/23$ 在数值上仍落在 Fly-By-Night-ISP 的 $200.23.16.0/20$ 之内，但它改由 ISPs-R-Us 接入 Internet。此时 Internet 中的路由器会同时收到两个能匹配该地址块目的地址的前缀：覆盖范围较宽的 $200.23.16.0/20$ 与覆盖范围较窄的 $200.23.18.0/23$。按最长前缀匹配的原则，目的地址落在 $200.23.18.0/23$ 内的分组应转发给 ISPs-R-Us，其余落在 $200.23.16.0/20$ 内但不落在 $200.23.18.0/23$ 内的分组转发给 Fly-By-Night-ISP。因此"更具体的路由"能够覆盖住某一聚合路由中的一小段地址，把该段改引到别处，而不必取消原来的聚合通告。

ISP 从何处获得地址块？答案是 **ICANN（Internet Corporation for Assigned Names and Numbers，互联网名称与数字地址分配机构）**，其职责为：分配地址（allocates addresses）；管理 DNS（manages DNS）；分配域名、解决争议（assigns domain names, resolves disputes）。其中第一项对应 IP 地址块的分配，是地址获取链条的最上层；后两项属于域名系统与名称管理。

#### 例题 Exercise-2：/30 子网中可接收特定目的地址的主机数（原页 5b-30）

**题干**：

> In subnet 192.168.4.0/30, the maximum number of hosts that can accept IP packets with destination address 192.168.4.3 is
> A. 0　　B. 1　　C. 2　　D. 4

即：在子网 $192.168.4.0/30$ 中，目的地址为 $192.168.4.3$ 的 IP 分组最多可被多少台主机接受？

**解**：

第 1 步：由前缀长度确定子网掩码。前缀长度为 30，故子网掩码前 30 位为 1、后 2 位为 0，按字节写出为 $255.255.255.252$。第三个字节 255 为全 1；第四个字节 $252=11111100_2$，后 2 位为 0，与 30 = 24 + 6 一致。

第 2 步：确定主机位数与地址总数。主机位数 $=32-30=2$，该子网共含 $2^{2}=4$ 个地址。

第 3 步：写出这 4 个地址。网络地址为 $192.168.4.0$，加上 0 至 3 的偏移，四个地址为 $192.168.4.0$、$192.168.4.1$、$192.168.4.2$、$192.168.4.3$。

第 4 步：逐地址判断性质。把第四个字节写成 8 位二进制并看其中后 2 位（主机位）：

- $192.168.4.0$：第四个字节 $0=00000000_2$，主机位 `00`，全 0 → 网络地址，不能分配给主机接口。
- $192.168.4.1$：第四个字节 $1=00000001_2$，主机位 `01` → 可用主机地址。
- $192.168.4.2$：第四个字节 $2=00000010_2$，主机位 `10` → 可用主机地址。
- $192.168.4.3$：第四个字节 $3=00000011_2$，主机位 `11`，全 1 → 定向广播地址，不能分配给主机接口。

第 5 步：区分“能否分配该地址”和“能否接收以该地址为目的的分组”。$192.168.4.3$ 不能分配给某一个主机接口，但它是本子网的广播地址。在本题的子网广播模型下，目的地址为该地址的分组可以由子网内所有主机接受，并不要求各主机自己的单播地址等于广播地址。

第 6 步：可用主机地址为 $192.168.4.1$、$192.168.4.2$，最多有 $2^2-2=2$ 台主机。因此，广播分组最多由这两台主机接受。

**答案**：**C. 2**。

**验证**：`.0` 是网络地址、`.3` 是广播地址，二者均不分配给主机；`.1`、`.2` 为两个有效单播地址。两台主机均可识别本子网广播目的地址 `.3`，故最多接受者为 2。题目问子网内的最大接受主机数，不能把“没有接口配置为 `.3`”误当作“没有主机接受发往 `.3` 的广播”。本题按正常接收子网广播的模型计数；具体系统的广播过滤设置并非题设条件。

### 5.6.6 网络地址转换（NAT: Network Address Translation，原页 5b-31 至 5b-35）

#### 拓扑与基本规则

NAT 用于把一个本地网络对外呈现为只使用一个 IP 地址。课件给出的拓扑为：

- 本地网络（local network，例如家庭网络）的地址块为 $10.0.0.0/24$。
- 本地网络内的主机接口地址为 $10.0.0.1$、$10.0.0.2$、$10.0.0.3$；NAT 路由器在本地网络一侧的接口地址为 $10.0.0.4$。
- NAT 路由器在"Internet 其余部分（rest of Internet）"一侧的接口地址为 $138.76.29.7$。

两条基本规则：

- 源地址或目的地址在本网络内的数据报，其源地址、目的地址照常使用 $10.0.0.0/24$ 中的地址。
- 所有离开本地网络的数据报都具有同一个源 NAT IP 地址 $138.76.29.7$，但使用不同的源端口号。

即本地网络内部通信仍使用 $10.0.0.0/24$ 的私有地址，NAT 的作用发生在数据报跨越 NAT 路由器边界时；外部网络只看到地址 $138.76.29.7$，看不到 $10.0.0.0/24$。

#### 动机与实现步骤

动机：就外部世界而言，本地网络只使用一个 IP 地址（local network uses just one IP address as far as outside world is concerned）。实现上，NAT 路由器必须完成三项操作：

1. 对出方向数据报（outgoing datagrams）：把（源 IP 地址, 端口号）替换为（NAT IP 地址, 新端口号）。
2. 在 NAT 转换表（NAT translation table）中记住每一个转换对（translation pair）。
3. 对入方向数据报（incoming datagrams）：把（NAT IP 地址, 新端口号）替换回 NAT 表中存储的对应（源 IP 地址, 端口号）。

第 1 项中“新端口号”指 NAT 对外使用的映射端口；它由映射规则确定，可以与原主机端口相同，也可以不同；第 3 项之所以能还原，依赖于第 2 项保存下来的转换对。转换对的双向使用是 NAT 能够区分多个内部主机共用同一外部地址的关键。

#### 一次完整的请求—应答过程

设主机 $10.0.0.1$ 访问服务器 $128.119.40.186$ 的 80 端口。

第 1 步：主机 $10.0.0.1$ 向 $128.119.40.186$ 的 80 端口发送数据报，地址字段为：

- 源：$10.0.0.1$，端口 $3345$
- 目的：$128.119.40.186$，端口 $80$

第 2 步：NAT 路由器把数据报的源地址从「$10.0.0.1$, $3345$」改为「$138.76.29.7$, $5001$」，并更新转换表：

| WAN side addr | LAN side addr |
|---------------|---------------|
| 138.76.29.7, 5001 | 10.0.0.1, 3345 |
| …… | …… |

（第二行的"……"表示该表可继续存放其他转换对。）修改后离开 NAT 路由器、进入 Internet 的数据报地址字段为：

- 源：$138.76.29.7$，端口 $5001$
- 目的：$128.119.40.186$，端口 $80$

第 3 步：应答到达，其目的地址为「$138.76.29.7$, $5001$」，地址字段为：

- 源：$128.119.40.186$，端口 $80$
- 目的：$138.76.29.7$，端口 $5001$

第 4 步：NAT 路由器把数据报的目的地址从「$138.76.29.7$, $5001$」改为「$10.0.0.1$, $3345$」，交给主机 $10.0.0.1$，地址字段为：

- 源：$128.119.40.186$，端口 $80$
- 目的：$10.0.0.1$，端口 $3345$

用原数据校验：第 2 步写入转换表的键值对是「WAN 侧 $138.76.29.7{:}5001$ ↔ LAN 侧 $10.0.0.1{:}3345$」；第 3 步到达的数据报目的端口恰为 $5001$，与表中 WAN 侧项匹配；第 4 步据此还原为 $10.0.0.1{:}3345$，与第 1 步原始源地址一致。整个往返过程中，内部主机 $10.0.0.1$ 及其端口 $3345$ 未被改动，外部服务器 $128.119.40.186{:}80$ 未察觉内部地址，端口号 $5001$ 是 NAT 路由器为该条连接分配的外部标识。

课件在本节脚注给出在线交互练习网址：`http://gaia.cs.umass.edu/kurose_ross/interactive/`。

#### 限制与保留地址

1. 在本节默认未预设入站映射的模型中，外部节点不能直接主动连接任意内部端点（Outside node cannot initiate the communication）。静态映射、端口转发等属于另加配置，不包含在这一默认模型中。原因是外部节点只能把数据报发往 NAT 的公共地址 $138.76.29.7$，而该地址下可能对应多个内部主机，外部节点在不知道 NAT 转换表内容的情况下无法指明内部主机及其端口，无法构造出会被 NAT 表匹配并转发的目的（地址, 端口）对。
2. 保留地址（Reserved addresses）：

| 保留地址范围 | 起始 | 结束 |
|--------------|------|------|
| 第一段 | 10.0.0.0 | 10.255.255.255 |
| 第二段 | 172.16.0.0 | 172.31.255.255 |
| 第三段 | 192.168.0.0 | 192.168.255.255 |

这三段地址即私有地址，它们不会在全球 Internet 中被分配为公网可路由地址，因此本地网络可以重复使用这些地址，NAT 路由器把它们统一映射到自己的公共地址上。本节 NAT 拓扑中的 $10.0.0.0/24$ 属于第一段；Exercise-2 中的 $192.168.4.0/30$ 属于第三段。

#### 规模与争议

1. 端口号字段为 16 位（16-bit port-number field）：使用单个 LAN 侧地址可以支持 60,000 个以上的并发连接（60,000+ simultaneous connections with a single LAN-side address）。依据是 16 位端口号的取值空间为 $2^{16}=65536$，扣除保留端口等后仍可支持六万余条并发连接。
2. NAT 是有争议的（NAT is controversial），课件列出四点理由：
   - 路由器本应只处理到第 3 层（routers should only process up to layer 3）。NAT 路由器需要读取并改写第 4 层的端口号，超出了网络层的处理范围。
   - 违反端到端原则（violates end-to-end argument）。由此带来的后果是：应用设计者必须把 NAT 的存在纳入考虑，例如 P2P 应用。
   - 地址短缺问题应由 IPv6 来解决（address shortage should be solved by IPv6）。
   - NAT 穿越问题（NAT traversal）：如果客户想要连接位于 NAT 之后的服务器，应如何处理。

### 5.6.7 LAN 地址与 ARP（原页 5b-36 至 5b-40）

#### IP 地址与 LAN 地址的分工

- **32 位 IP 地址（32-bit IP address）**：
  - network-layer address（网络层地址）。
  - 用于把数据报送到目的网络（used to get datagram to destination network）。
- **LAN 地址（LAN address，又称 MAC 地址或物理地址，MAC or physical address）**：
  - 用于把数据报从一个接口送到与之物理连接的另一接口（used to get datagram from one interface to another physically-connected interface），即同一网络（same network）内的寻址。
  - 大多数 LAN 使用 48 位 MAC 地址（48 bit MAC address），烧录在网卡 ROM 中（burned in the adapter ROM）。
  - 示例：`1A-2F-BB-76-09-AD`。

两类地址的书写格式不同：IP 地址为点分十进制（如 $137.196.7.23$），MAC 地址为 6 组两位十六进制、以连字符分隔（如 `1A-2F-BB-76-09-AD`）。二者在转发中作用范围不同：IP 地址用于跨网络的端到端寻址，MAC 地址用于同一物理网络内一跳到下一跳的寻址。

#### 每个适配器有唯一的 LAN 地址

局域网上连接多台主机，每台主机的适配器（adapter）都有一个唯一的 LAN 地址。课件图示中标出的四个地址为：

- `1A-2F-BB-76-09-AD`（上方主机）
- `58-23-D7-FA-20-B0`（右侧主机）
- `0C-C4-11-6F-E3-98`（下方主机）
- `71-65-F7-2B-08-53`（左侧主机）

这四个地址互不相同，对应"Each adapter on LAN has unique LAN address"。同一台主机更换适配器后，其 LAN 地址随之改变；而 IP 地址由所在网络/子网决定，与适配器本身无关。

#### MAC 地址的分配与可携带性

- MAC 地址的分配由 IEEE 管理（MAC address allocation administered by IEEE）。
- 制造商购买一部分 MAC 地址空间（manufacturer buys portion of MAC address space），以保证唯一性（to assure uniqueness）。
- 课件给出的对照表述为：（a）MAC 地址——社会保险号；（b）IP 地址——邮政地址。据此说明两点差别：
  - MAC 地址是扁平地址（MAC flat address），因此具有可携带性（portability）：可以把一块 LAN 卡从一处 LAN 移到另一处 LAN，其 MAC 地址不变。
  - IP 地址是层次化地址（IP hierarchical address），不可携带（NOT portable）：它取决于节点所接入的 IP 子网（depends on IP subnet to which node is attached），节点换到另一个子网后必须改用该子网的地址。

上述对照是课件原有的表述，其直接含义为：MAC 地址的取值空间被统一编号后按制造商分割，不包含位置信息；IP 地址的前缀部分由节点所在子网决定，两者在"是否随位置改变"这一点上相反。

#### ARP 模块、ARP 表与 TTL

ARP（Address Resolution Protocol，地址解析协议）解决的问题是：在已知某节点的 IP 地址时，如何确定其 MAC 地址（how to determine MAC address of B given B's IP address）。

- LAN 上的每个 IP 节点（主机、路由器）都有 ARP 模块与 ARP 表（Each IP node (Host, Router) on LAN has ARP module, table）。
- ARP 表存放部分 LAN 节点的 IP/MAC 地址映射（IP/MAC address mappings for some LAN nodes），表项格式为

$$\langle \text{IP address};\ \text{MAC address};\ \text{TTL} \rangle$$

- TTL（Time To Live）：地址映射被遗忘的时间（time after which address mapping will be forgotten），典型值为 20 分钟（typically 20 min）。

课件图示标出的四个节点的 IP 与 MAC 对应关系为：

| IP 地址 | MAC 地址 | 图中位置 |
|---------|----------|----------|
| 137.196.7.23 | 71-65-F7-2B-08-53 | 左侧主机 |
| 137.196.7.78 | 1A-2F-BB-76-09-AD | 上方主机 |
| 137.196.7.14 | 58-23-D7-FA-20-B0 | 右侧主机 |
| 137.196.7.88 | 0C-C4-11-6F-E3-98 | 下方主机 |

四个 IP 地址同属 $137.196.7.0/24$（前三个字节相同），说明这四个节点在同一 LAN 内。ARP 表并非全 LAN 节点的完整清单，只保存"部分节点"（some LAN nodes）的映射，未保存的映射需要通过 ARP 解析获得。

#### 同一 LAN 内 ARP 的解析过程

设主机 A 要向主机 B 发送数据报，但 A 的 ARP 表中没有 B 的 MAC 地址。

1. A 广播 ARP 查询分组（A broadcasts ARP query packet），分组中包含 B 的 IP 地址。
   - 该分组的目的 MAC 地址为 `FF-FF-FF-FF-FF-FF`（广播地址）。
   - LAN 上所有节点都会收到该 ARP 查询。
2. B 收到该 ARP 分组后，以自己的 MAC 地址回复 A（B receives ARP packet, replies to A with its (B's) MAC address）。
   - 该回复帧以 A 的 MAC 地址为目的地址发送，即单播（unicast）。
3. A 把这一"IP 到 MAC 的地址对"缓存（caches）到自己的 ARP 表中，直到该信息超时为止。
   - 这种信息称为软状态（soft state）：除非被刷新，否则会超时消失（information that times out (goes away) unless refreshed）。
4. ARP 是"即插即用"（plug-and-play）：节点自己建立 ARP 表，无需网络管理员干预（nodes create their ARP tables without intervention from net administrator）。

关键点在于查询用广播、应答用单播：查询时 A 不知道 B 的 MAC 地址，只能发往广播地址 `FF-FF-FF-FF-FF-FF`；应答时 B 已知 A 的 MAC 地址（从查询帧的源 MAC 字段得到），因此可以直接单播。TTL 机制使 ARP 表项不会永久保留，适应节点更换适配器或移动的情况，这正是 ARP 无需管理员维护的原因。

### 5.6.8 跨局域网寻址与转发：主机 A 经路由器 R 向主机 B 发送数据报（原页 5-41 至 5-46、5b-47）

#### 场景设定与拓扑地址

场景为：主机 A 发送一个数据报，经路由器 R 转发，送达主机 B。课件列出四条前提：

- focus on addressing – at IP (datagram) and MAC layer (frame)：关注寻址问题，即 IP 层（数据报）与 MAC 层（帧）两个层次上的地址。
- assume A knows B's IP address：假定 A 已知 B 的 IP 地址。
- assume A knows IP address of first hop router, R (how?)：假定 A 已知第一跳路由器 R 的 IP 地址（课件以 "(how?)" 提问其来源）。
- assume A knows R's MAC address (how?)：假定 A 已知 R 的 MAC 地址（课件同样以 "(how?)" 提问其来源）。

拓扑中出现的全部接口及其地址：

| 设备/接口 | IP 地址 | MAC 地址 |
|---|---|---|
| 主机 A | 111.111.111.111 | 74-29-9C-E8-FF-55 |
| A 所在局域网内的另一台主机 | 111.111.111.112 | CC-49-DE-D0-AB-7D |
| 路由器 R 面向 A 一侧的接口 | 111.111.111.110 | E6-E9-00-17-BB-4B |
| 路由器 R 面向 B 一侧的接口 | 222.222.222.220 | 1A-23-F9-CD-06-9B |
| 主机 B | 222.222.222.222 | 49-BD-D2-C7-56-2A |
| B 所在局域网内的另一台主机 | 222.222.222.221 | 88-B2-2F-54-1A-0F |

由地址可以看出：A 与其网关接口 111.111.111.110 处于同一个 IP 网络（前 24 位相同，即 111.111.111.0/24）；B 与其网关接口 222.222.222.220 处于同一个 IP 网络（222.222.222.0/24）。R 是唯一连接两个 IP 网络的设备，因此 A 到 B 的通信必须经 R 转发，不可能由 A 直接向 B 发送链路层帧。

对课件提出的两个 "(how?)"，按本课程此前已建立的机制补充说明（非源页文字）：

- A 如何得知 B 的 IP 地址：由应用层提供，例如用户在浏览器中输入域名后经 DNS 解析得到，或由应用程序直接给出目的 IP。
- A 如何得知第一跳路由器 R 的 IP 地址：由主机的手工配置或 DHCP 下发，即主机的"默认网关（default gateway）"配置项，其值在此拓扑中为 111.111.111.110。
- A 如何得知 R 的 MAC 地址：由 ARP 解析得到，即 A 在本局域网内广播 ARP 请求查询 111.111.111.110 对应的 MAC 地址，R 的该接口以自己的 MAC 地址 E6-E9-00-17-BB-4B 单播应答。

#### 逐步转发过程

课件用连续多页展示同一次发送的封装与解封装过程，其中三页文字与图中标注完全相同，属于同一动画步骤的重复帧，此处合并为第 3 步。

**第 1 步：A 封装数据报与帧**

- A creates IP datagram with IP source A, destination B —— A 生成 IP 数据报，IP 源地址为 A，目的地址为 B。
- A creates link-layer frame with R's MAC address as destination address, frame contains A-to-B IP datagram —— A 生成链路层帧，以 R 的 MAC 地址作为目的地址，帧中封装 A 到 B 的 IP 数据报。

图中标注的字段值：

- IP src: 111.111.111.111
- IP dest: 222.222.222.222
- MAC src: 74-29-9C-E8-FF-55
- MAC dest: E6-E9-00-17-BB-4B

A 的协议栈自上而下为 IP、Eth、Phy；IP 首部的地址来自网络层，Eth 首部的地址来自链路层；帧中承载的整个内容就是 A 到 B 的 IP 数据报。关键点是：**IP 数据报的目的地址是最终目的主机 B，而帧的目的地址是下一跳路由器 R 的接口**。两者的目的对象不同，这是本次转发全部后续行为的根据。

**第 2 步：帧从 A 发送到 R，R 接收并解封装**

- frame sent from A to R —— 帧从 A 发送到 R。
- frame received at R, datagram removed, passed up to IP —— 帧在 R 处被接收，数据报被取出，上交给 IP 层。

本页图中 A 侧帧的标注仍为 MAC src 74-29-9C-E8-FF-55、MAC dest E6-E9-00-17-BB-4B、IP src 111.111.111.111、IP dest 222.222.222.222；R 的协议栈同样为 IP、Eth、Phy 三层，数据报经 Eth 上交到 IP。

**第 3 步：R 转发并重新封装帧**

- R forwards datagram with IP source A, destination B —— R 转发 IP 源为 A、目的为 B 的数据报。
- R creates link-layer frame with B's MAC address as destination address, frame contains A-to-B IP datagram —— R 生成链路层帧，以 B 的 MAC 地址作为目的地址，帧中封装 A 到 B 的 IP 数据报。

图中标注的字段值：

- MAC src: 1A-23-F9-CD-06-9B
- MAC dest: 49-BD-D2-C7-56-2A
- IP src: 111.111.111.111
- IP dest: 222.222.222.222

MAC src 取的是 R 面向 B 一侧接口的 MAC 地址（1A-23-F9-CD-06-9B），而不是面向 A 一侧接口的地址（E6-E9-00-17-BB-4B），因为帧是从该出口接口发出的。IP 源与目的地址在这两跳中完全不变。（课件此处另给出在线交互练习链接 `http://gaia.cs.umass.edu/kurose_ross/interactive/`，非知识点内容。）

#### 两层地址在各跳的变化

| 阶段 | 链路层源地址（MAC src） | 链路层目的地址（MAC dest） | 网络层源地址（IP src） | 网络层目的地址（IP dest） |
|---|---|---|---|---|
| 帧在 A→R 链路上（A 发出） | 74-29-9C-E8-FF-55（A） | E6-E9-00-17-BB-4B（R 的入口接口） | 111.111.111.111（A） | 222.222.222.222（B） |
| 帧在 R→B 链路上（R 发出） | 1A-23-F9-CD-06-9B（R 的出口接口） | 49-BD-D2-C7-56-2A（B） | 111.111.111.111（A） | 222.222.222.222（B） |

由此得到两条结论：

1. **IP 地址端到端不变**：源 IP 与目的 IP 在整个转发路径上始终指向通信的两端主机；它们是"端到端"的地址，用于确定数据报最终要送到哪个网络接口所属的主机。
2. **MAC 地址逐跳改变**：每一跳的帧，其源 MAC 与目的 MAC 分别取发送接口与接收接口的链路层地址；它们是"逐跳"的地址，只在一个局域网范围内有意义，用于把帧送到链路上的某个具体适配器。

上述过程还隐含一步课件未展开、但由图意直接给出的动作：R 的 IP 层根据目的地址 222.222.222.222 查转发表，判定出口是面向 B 的接口（地址 222.222.222.220），随后才有第 3 步的重新封装。R 在此过程中不修改 IP 源地址与目的地址（补充说明：若 R 同时执行 NAT，则源地址会被改写，这与 5.6.6 节的网络地址转换是另一个独立机制，本场景未启用）。

#### 例题 Exercise-3：以太网帧首部解析与转发字段判定（原页 5b-47）

**题干**：

> Exercise-3. Figure 1 shows the network topology, and Figure 2 shows the hex-content of the first 80 bytes of an Ethernet frame of the host for a Web request.
>
> (1) What is the IP address of the Web server? What is the MAC address of the default gateway of this host?
>
> (2) When the IP packet encapsulated in this frame is forwarded through router R, which fields in the IP packet need to be modified?

**图 1 信息**：一台主机（Web 客户）的 IP 地址为 10.2.128.100，经路由器 R 接入 Internet。R 的两个接口地址分别为 10.2.128.1（面向主机的内侧）与 101.12.123.15（面向 Internet 的外侧）。外侧链路上标注 MTU = 1500B。

**图 2 信息**：该主机发出的以太网帧的前 80 字节十六进制内容，共 5 行、每行 16 字节（已核对原图，逐行完整抄录）：

```
00 21 27 21 51 ee 00 15 c5 c1 5e 28 08 00 45 00
01 ef 11 3b 40 00 80 06 ba 9d 0a 02 80 64 40 aa
62 20 04 ff 00 50 e0 e2 00 fa 7b f9 f8 05 50 18
fa f0 1a c4 00 00 47 45 54 20 2f 72 66 63 2e 68
74 6d 6c 20 48 54 54 50 2f 31 2e 31 0d 0a 41 63
```

**解**：

第 1 步：按以太网帧格式划分前 14 字节。以太网帧首部为 6 字节目的 MAC、6 字节源 MAC、2 字节类型，共 14 字节。

- 字节 0～5：`00 21 27 21 51 ee` → 目的 MAC 地址 = 00:21:27:21:51:EE
- 字节 6～11：`00 15 c5 c1 5e 28` → 源 MAC 地址 = 00:15:C5:C1:5E:28
- 字节 12～13：`08 00` → 类型字段 = 0x0800，表示上层承载的是 IPv4 数据报（若是 0x0806 则为 ARP，0x86DD 则为 IPv6）

第 2 步：定位 IPv4 首部，从字节 14 开始逐字段取值。IPv4 首部固定部分 20 字节（字节 14～33）：

| 字节位置 | 十六进制值 | 字段 | 译码结果 |
|---|---|---|---|
| 14 | 45 | 版本 + 首部长度 | 版本 = 4；首部长度 = 5，即 5×4 = 20 字节 |
| 15 | 00 | 区分服务（TOS） | 0x00 |
| 16～17 | 01 ef | 总长度 | 0x01EF = 495 字节 |
| 18～19 | 11 3b | 标识 | 0x113B = 4411 |
| 20～21 | 40 00 | 标志 + 片偏移 | 0x4000，即 DF=1、MF=0、片偏移 = 0 |
| 22 | 80 | 生存时间 TTL | 128 |
| 23 | 06 | 协议 | 6 = TCP |
| 24～25 | ba 9d | 首部校验和 | 0xBA9D = 47773 |
| 26～29 | 0a 02 80 64 | 源 IP 地址 | 10.2.128.100 |
| 30～33 | 40 aa 62 20 | 目的 IP 地址 | 64.170.98.32 |

地址换算过程：`0a 02 80 64`：0x0A=10、0x02=2、0x80=128、0x64=100，故为 10.2.128.100；`40 aa 62 20`：0x40=64、0xAA=170、0x62=98、0x20=32，故为 64.170.98.32。总长度 0x01EF = $1\times256+14\times16+15=256+224+15=495$ 字节。

第 3 步：判定这一帧的目的 MAC 属于谁。题图明确给出主机经路由器 R 访问 Internet 上的 Web 服务器，因此主机先将帧交给默认网关，帧的目的 MAC 是 R 内侧接口的 MAC。由帧首部可得 **00:21:27:21:51:EE**。题图没有给出子网掩码，不能仅凭地址的前三个字节相同就断言该 LAN 使用 /24 前缀。

第 4 步：确定 Web 服务器的 IP 地址。该帧承载的是主机发出的请求报文，其 IP 目的地址即被请求的服务器地址，故 Web 服务器的 IP 地址 = **64.170.98.32**。该结论可用第 5 步的传输层信息交叉验证。

第 5 步：验证"这是一次 Web 请求"。IPv4 首部 20 字节之后（字节 34 起）是 TCP 首部，共 20 字节（字节 34～53）：

| 字节位置 | 十六进制值 | 字段 | 译码结果 |
|---|---|---|---|
| 34～35 | 04 ff | 源端口 | 0x04FF = 1279 |
| 36～37 | 00 50 | 目的端口 | 0x0050 = 80 |
| 38～41 | e0 e2 00 fa | 序号 | 0xE0E200FA |
| 42～45 | 7b f9 f8 05 | 确认号 | 0x7BF9F805 |
| 46～47 | 50 18 | 首部长度 + 标志 | 首部长度 = 5，即 20 字节；标志 PSH=1、ACK=1 |
| 48～49 | fa f0 | 窗口 | 0xFAF0 = 64240 |
| 50～51 | 1a c4 | 校验和 | 0x1AC4 |
| 52～53 | 00 00 | 紧急指针 | 0 |

目的端口为 80，即 HTTP 服务端口，与题干 "a Web request" 一致，说明该帧确实是发往 Web 服务器的请求，其目的 IP 64.170.98.32 就是 Web 服务器地址。

第 6 步：读取应用层数据。帧被截取的长度为 80 字节，减去以太网首部 14 字节、IPv4 首部 20 字节、TCP 首部 20 字节，得数据部分 $80-14-20-20=26$ 字节，位于字节 54～79：

```
47 45 54 20 2f 72 66 63 2e 68 74 6d 6c 20 48 54 54 50 2f 31 2e 31 0d 0a 41 63
```

按 ASCII 译码：47='G'、45='E'、54='T'、20=' '(空格)、2f='/'、72='r'、66='f'、63='c'、2e='.'、68='h'、74='t'、6d='m'、6c='l'、20=' '、48='H'、54='T'、54='T'、50='P'、2f='/'、31='1'、2e='.'、31='1'、0d=CR、0a=LF、41='A'、63='c'。得到字符串 `GET /rfc.html HTTP/1.1\r\nAc`（末尾 "Ac" 为下一行首部字段的开头，被 80 字节截断）。这是 HTTP 请求行，请求对象为 /rfc.html，协议版本 HTTP/1.1，与第 5 步结论一致。

第 7 步（第 (2) 问）：判断路由器 R 转发该 IP 分组时需要修改哪些字段。

首先确认不需要分片。图 1 标注外侧链路 MTU = 1500B，而该 IP 数据报总长度仅 495 字节，$495<1500$，且 DF=1 也不会造成问题，因此 R 不执行分片，标识（0x113B）、标志（0x4000）、片偏移（0）三个字段保持原值不变。

必须修改的字段为：

1. **生存时间 TTL**：数据报每经过一个路由器，TTL 减 1（减为 0 时丢弃该数据报并回送 ICMP 超时报文）。故 TTL 由 128 变为 127，即字节 22 由 0x80 变为 0x7F。
2. **首部校验和**：因为 TTL 发生变化，首部校验和必须重新计算。原值为 0xBA9D，新值为 0xBB9D，计算过程见下。

其余字段不变：源 IP 地址 10.2.128.100、目的 IP 地址 64.170.98.32 均不改写；协议字段（6 = TCP）不改写；总长度（495）不改写；区分服务与 TCP 首部全部字段不改写。

**首部校验和的完整验算**（先验证原值，再算新值）：

IPv4 首部校验和的规则是：把首部按 16 位分组，校验和字段本身置 0，各位相加（采用反码求和，即最高位进位回卷加到最低位），最后取反。

原首部的 10 个 16 位字为：0x4500、0x01EF、0x113B、0x4000、0x8006、0xBA9D、0x0A02、0x8064、0x40AA、0x6220。把校验和字 0xBA9D 视为 0，其余九项累加：

- 0x4500 + 0x01EF = 0x46EF
- 0x46EF + 0x113B = 0x582A
- 0x582A + 0x4000 = 0x982A
- 0x982A + 0x8006 = 0x11830
- 0x11830 + 0x0A02 = 0x12232
- 0x12232 + 0x8064 = 0x1A296
- 0x1A296 + 0x40AA = 0x1E340
- 0x1E340 + 0x6220 = 0x24560

回卷进位：把 0x24560 的高 16 位与低 16 位相加，得 0x4560 + 0x0002 = 0x4562。取反：0xFFFF − 0x4562 = 0xBA9D。结果与帧中字节 24～25 的 `ba 9d` 完全一致，说明原始首部在发送时是正确无误的。

TTL 由 0x80 改为 0x7F 后，第 5 个 16 位字由 0x8006 变为 0x7F06，即总和减少了 0x8006 − 0x7F06 = 0x0100：

- 新的累加和 = 0x24560 − 0x0100 = 0x24460
- 回卷进位：0x4460 + 0x0002 = 0x4462
- 取反：0xFFFF − 0x4462 = 0xBB9D

故转发后首部校验和为 0xBB9D。

用原始数据反过来校验新值：把转发后首部的十个字（TTL 已变为 0x7F，校验和取新值 0xBB9D）全部相加，结果应为 0xFFFF：

- 0x4500 + 0x01EF = 0x46EF
- 0x46EF + 0x113B = 0x582A
- 0x582A + 0x4000 = 0x982A
- 0x982A + 0x7F06 = 0x11730
- 0x11730 + 0xBB9D = 0x1D2CD
- 0x1D2CD + 0x0A02 = 0x1DCCF
- 0x1DCCF + 0x8064 = 0x25D33
- 0x25D33 + 0x40AA = 0x29DDD
- 0x29DDD + 0x6220 = 0x2FFFD
- 回卷进位：0xFFFD + 0x0002 = 0xFFFF

结果为 0xFFFF，校验通过，新校验和 0xBB9D 正确。

第 8 步：说明不属于本题答案范围的地址变化（避免混淆层次）。R 转发后，承载该数据报的以太网帧的源 MAC 与目的 MAC 必然改变（源 MAC 换为 R 外侧接口的 MAC，目的 MAC 换为下一跳的 MAC），目的 IP 不变。但这些 MAC 字段属于链路层帧首部，题干问的是 "the fields in the IP packet"，因此不列入答案。

补充说明（非源题条件）：源 IP 为 10.2.128.100，属私有地址范围 10.0.0.0～10.255.255.255。若该路由器同时启用了 NAT（网络地址转换），则转发时还要改写源 IP 地址，并可能改写 TCP 源端口，随之 TCP 与 IP 校验和也需重算。但原题既未说明 NAT 已启用，也未给出 NAT 后的公网地址，仅凭源地址是私有地址不足以断定本场景一定执行 NAT，故本题答案以上述 TTL 与首部校验和两项为准。

**答案**：

(1) Web 服务器的 IP 地址为 **64.170.98.32**；该主机默认网关（路由器 R 内侧接口）的 MAC 地址为 **00:21:27:21:51:EE**。

(2) 该 IP 分组经路由器 R 转发时需要修改的字段是：**TTL（由 128 减为 127）** 与 **IPv4 首部校验和（由 0xBA9D 改为 0xBB9D）**。标识、标志、片偏移、总长度、协议、源 IP 地址、目的 IP 地址均不变（本分组 495 字节小于 MTU 1500 字节，不需分片）。

### 5.6.9 ICMP：互联网控制报文协议（原页 5-48、5b-49 至 5b-52）

#### ICMP 在网络层中的位置与报文构成（原页 5-48、5b-49）

ICMP（Internet Control Message Protocol，互联网控制报文协议）的定位：

- used by hosts, routers, gateways to communication network-level information —— 被主机、路由器、网关用于传递网络层信息。其用途分为两类：
  - error reporting: unreachable host, network, port, protocol —— 差错报告：主机不可达、网络不可达、端口不可达、协议不可达。
  - echo request/reply (used by ping) —— 回送请求/回送应答（供 ping 使用）。
- network-layer "above" IP —— 位于 IP 的"上层"（指同属网络层但承载在 IP 之内的一层）。
  - ICMP msgs carried in IP datagrams —— ICMP 报文封装在 IP 数据报中传输。
- ICMP message: type, code plus first 8 bytes of IP datagram causing error —— ICMP 报文的构成是：类型（type）、代码（code），再加引起差错的 IP 数据报的前 8 个字节。

由此可确认 ICMP 的三项基本性质：它是网络层协议；它不使用独立的传输层协议承载，而是直接作为 IP 数据报的数据部分；它不传递用户数据，只传递关于网络层自身运行状态的控制信息。报文携带"引起差错的数据报的前 8 个字节"，是为了让收到差错报告的源主机能够识别是哪一个数据报出了问题（前 8 字节中含源端口、目的端口等用于匹配的信息）。

课件对该协议给出简短总结：

- ICMP is the control sibling of IP —— ICMP 是 IP 的控制协议伴体。
- ICMP is used by IP and uses IP as network layer protocol —— ICMP 被 IP 使用，同时又把 IP 作为它的网络层承载协议。
- ICMP is used for ping, traceroute, and path MTU discovery —— ICMP 用于 ping、traceroute 和路径 MTU 发现。
- Ping: uses ICMP Echo request/reply messages —— ping 使用 ICMP 回送请求/回送应答报文。

| Type | Code | description |

| 0 | 0 | echo reply (ping) |
| 3 | 0 | dest. network unreachable |
| 3 | 1 | dest host unreachable |
| 3 | 2 | dest protocol unreachable |
| 3 | 3 | dest port unreachable |
| 3 | 6 | dest network unknown |
| 3 | 7 | dest host unknown |
| 4 | 0 | source quench (congestion control - not used) |
| 8 | 0 | echo request (ping) |
| 9 | 0 | route advertisement |
| 10 | 0 | router discovery |
| 11 | 0 | TTL expired |
| 12 | 0 | bad IP header |

表中共 13 行。按类型归并可以看出其结构：类型 0 与 8 成对构成 echo reply 与 echo request，供 ping 使用；类型 3 的 6 行代码（0、1、2、3、6、7）都表示"目的不可达"这一类差错，代码区分不可达的具体原因（网络、主机、协议、端口、网络未知、主机未知）；类型 4 的 source quench 是早期的拥塞控制机制，课件明确标注为 "not used"（不再使用）；类型 11（TTL expired）与类型 12（bad IP header）都是路由器在转发过程中发现问题时回报的差错；类型 9 与 10 用于路由器的通告与发现。其中与本节后续内容直接相关的是：类型 11（TTL 超时，被 traceroute 利用）、类型 3 代码 3（端口不可达，被 traceroute 用作终止条件）、类型 8 与 0（回送请求/应答，被 ping 使用）。

#### ping 的运行过程与实例（原页 5b-50）

ping 的工作方式是：源主机向目的主机发送 ICMP 类型 8（回送请求）报文，目的主机收到后回送 ICMP 类型 0（回送应答）报文；源主机根据发出与收到的时间差计算往返时延 RTT（round-trip time）。课件给出的运行结果为：

- 第一行是命令 `ping mail.sina.com.cn`，命令行提示符显示当前工作目录为 C:\Documents and Settings\XXR。

#### 路径 MTU 发现（原页 5b-49）

路径 MTU 发现的两个步骤：

- Send a large IP datagram with "No fragment" bit set —— 发送一个设置了"不分片"比特的大 IP 数据报（即 IPv4 首部中的 DF=1）。
- Reduce size until success (No ICMP message received) —— 逐步减小尺寸直到成功（即不再收到 ICMP 报文）为止。

其依据是：当路由器收到一个 DF=1 且长度超过出接口 MTU 的数据报时，无法分片，只能丢弃并回送一个 ICMP 差错报文（类型 3 的相应代码）告知源主机。源主机可根据 ICMP 差错中提供的 MTU 信息调整数据报长度，并继续探测。路径 MTU 是沿途各链路 MTU 的最小值；某个长度的探测成功，只能说明该长度可通过，不能单凭一次成功就断定它等于路径 MTU。还需结合差错反馈或对可通过长度上界的搜索。仅“不再收到 ICMP 报文”也不能证明探测成功，因为探测包或 ICMP 反馈可能丢失或被过滤。

#### traceroute 的运行过程与实例（原页 5b-51、5b-52）

traceroute 的探测过程：

- Source sends series of UDP segments to dest. —— 源端向目的端发送一系列 UDP 报文段。
  - First has TTL=1 —— 第一个数据报的 TTL=1。
  - Second has TTL=2, etc. —— 第二个的 TTL=2，依此类推。
  - Unlikely port number —— 使用一个不太可能被使用的（目的）端口号。
- When nth datagram arrives to nth router: —— 当第 n 个数据报到达第 n 个路由器时：
  - Router discards datagram —— 路由器丢弃该数据报（因为 TTL 减到 0）。
  - And sends to source an ICMP message (type 11, code 0) —— 并向源端发送一个 ICMP 报文（类型 11，代码 0，即 TTL 超时）。
  - Message includes name of router & IP address —— 该报文包含路由器的名字与 IP 地址。
- When ICMP message arrives, source calculates RTT —— 当 ICMP 报文到达时，源端计算 RTT。
- Traceroute does this 3 times —— traceroute 对每一跳这样做 3 次（每跳发送 3 个探测报文，用于降低偶然误差的影响，这也解释了输出中每跳为何有三个时延值）。
- 停止条件（Stopping criterion）：
  - UDP segment eventually arrives at destination host —— UDP 报文段最终到达目的主机。
  - Destination returns ICMP "port unreachable" packet (type 3, code 3) —— 目的主机返回 ICMP "端口不可达"报文（类型 3，代码 3）。
  - When source gets this ICMP, stops —— 源端收到该 ICMP 报文后停止。

两个机制的配合需要说明清楚：探测报文使用 UDP 承载并故意选用一个不太可能被使用的目的端口号，是为了让目的主机在收到探测报文时必然回送"端口不可达"差错，从而使源端能够识别"已经到达终点"。中间各跳的路由器并不知道这是探测报文，它们只是按 TTL 规则正常处理：TTL 减到 0 就丢弃并回送类型 11 代码 0 的 ICMP 超时报文，该报文中带有该路由器的名字与 IP 地址——这正是 traceroute 能够逐跳列出路径的原因。

### 5.6.10 IPv6（原页 5b-53 至 5b-60）

#### 引入动机与总体特征（原页 5b-53）

- Initial motivation: 32-bit address space soon to be completely allocated. —— 初始动机：32 位地址空间即将被完全分配完。
- Additional motivation: —— 附加动机：
  - header format helps speed processing/forwarding —— 首部格式有助于加快处理与转发速度。
  - header changes to facilitate QoS —— 首部的改变便于支持服务质量（QoS，Quality of Service）。
  - new "anycast" address: route to "best" of several replicated servers —— 新增"任播（anycast）"地址：把报文路由到若干个复制服务器中"最好的"一个。
- IPv6 datagram format: —— IPv6 数据报格式：
  - fixed-length 40 byte header —— 固定长度 40 字节的首部。
  - no fragmentation allowed —— 不允许分片。

因果关系是：IPv4 的地址字段宽度为 32 位，可编址总量有限；当地址空间接近耗尽时，仅靠地址分配技巧（如 CIDR、NAT）已不足以长期维持，因此需要直接扩大地址字段宽度，这是 IPv6 把地址字段定为 128 位的直接原因。附加动机与地址宽度无关：固定长度首部使路由器无需按可变的选项字段做判断即可完成转发处理；首部中新增的优先级与流标签字段为按流提供差异化服务提供了字段级支持；anycast 地址为多台复制服务器共用一个地址、由路由把请求导向其中最优一台提供了地址类型支持。

关于 "no fragmentation allowed" 这一表述，需要结合扩展首部结构准确理解（补充说明）：IPv6 的基本首部中不含分片相关字段，沿途路由器不对数据报执行分片；分片改由源端完成，方法是附加一个分片扩展首部（Fragment header）。因此扩展首部链中会出现 "Fragment header"，与本页"不允许分片"并不矛盾——后者指的是沿途路由器不再分片。

#### IPv6 首部格式（原页 5b-54）

三个字段的含义：

- Priority: identify priority among datagrams in flow —— 优先级：标识同一个流中各数据报之间的优先级。
- Flow Label: identify datagrams in same "flow." (concept of "flow" not well defined). —— 流标签：标识属于同一个"流"的数据报（课件注明"流"的概念尚未被良好地定义）。
- Next header: identify upper layer protocol for data —— 下一个首部：标识数据部分的上一层协议。

首部结构按 32 位宽逐行排布为：

| 行 | 内容（从左到右） |
|---|---|
| 第 1 行（32 位） | ver ｜ pri ｜ flow label |
| 第 2 行（32 位） | payload len ｜ next hdr ｜ hop limit |
| 第 3 行 | source address (128 bits)，占 4 行 32 位 |
| 第 4 行 | destination address (128 bits)，占 4 行 32 位 |
| 之后 | data |

补充说明（课件图未标注，按 IPv6 标准给出比特分配）：version 占 4 位；priority（标准中称 traffic class，通信量类）占 8 位；flow label（流标签）占 20 位，三者合计 $4+8+20=32$ 位，构成第一行。第二行中 payload len（净荷长度）占 16 位，next hdr（下一个首部）占 8 位，hop limit（跳数限制）占 8 位，合计 32 位。源地址 128 位、目的地址 128 位各占 4 行。基本首部总计 40 字节，与"fixed-length 40 byte header"一致。

几个字段与 IPv4 的对应关系：

- version（版本）：IPv6 取值为 6；作用是让接收端识别首部按哪一种格式解析，其位置与作用同 IPv4 首部的版本字段。
- priority（优先级）：在同一个流内区分数据报的优先级。这是 IPv6 新增的字段，IPv4 首部中无对应字段（IPv4 的 TOS 字段虽在后期被用于区分服务，但课件未作此对应说明）。
- flow label（流标签）：标识同属一个流的数据报。课件明确说明"流"的概念尚未被良好定义，本课件不作进一步展开。
- payload len（净荷长度）：对应 IPv4 的总长度字段，但 IPv6 中它表示首部之后有效载荷的长度，而不含 40 字节基本首部本身。
- next hdr（下一个首部）：标识数据部分的上一层协议，作用与 IPv4 的协议字段相当，但因 IPv6 引入扩展首部链，其取值既可指向传输层协议（如 TCP、UDP），也可指向某个扩展首部。
- hop limit（跳数限制）：对应 IPv4 的 TTL，每经过一个路由器减 1，减为 0 时丢弃数据报；IPv6 用"跳数"命名，其含义即剩余可经过的路由器跳数。
- 与 IPv4 相比，IPv6 基本首部中不出现首部长度（因首部固定 40 字节，无需表示）、标识、标志、片偏移（因路由器不分片）、首部校验和等字段。

#### 扩展首部与 Next Header 链（原页 5b-55）

**情形一：不带扩展首部（Without extension header）**。基本首部之后直接是 TCP/UDP 首部与数据（即 TCP/UDP 报文段）。基本首部内的 Next header 字段取值为 "= TCP/UDP"，指向后面的 TCP/UDP header and data。图中标注的 "Effective payload"（有效载荷）范围从基本首部之后开始，一直延伸到数据报末尾，即只包含 TCP/UDP 报文段本身。

**情形二：带扩展首部（With extension header）**。基本首部之后依次为路由首部、分片首部，再之后才是 TCP/UDP 首部与数据：

| 首部 | 其中的 Next header 取值 | 指向 |
|---|---|---|
| Basic header（基本首部） | = routing selection（路由选择） | Routing header |
| Routing header（路由首部） | = fragment（分片） | Fragment header |
| Fragment header（分片首部） | = TCP/UDP | TCP/UDP header and data |
| TCP/UDP header and data (TCP/UDP segment) | — | 数据报结尾 |

图中标注的 "Effective payload" 范围从基本首部之后开始，覆盖整条扩展首部链与 TCP/UDP 报文段，直到数据报末尾。

两种情形对照可以得到 Next header 字段的作用规律：它构成一条链。基本首部中的 Next header 指出紧随其后的是传输层首部还是某一种扩展首部；若是扩展首部，则该扩展首部自身也带有 Next header 字段，继续指出下一个首部是什么，直到某个 Next header 取值指向传输层协议（TCP/UDP），其后即为用户数据。接收端沿这条链依次处理，遇到不认识的 Next header 值即可按规则处理，而不必解析全部内容。

这一结构也是"选项被移到首部之外"的实现方式：IPv4 中可变的选项字段被移出固定首部，改由扩展首部承载，通过 Next header 链按需插入，从而使基本首部得以保持固定 40 字节。

#### 相对 IPv4 的其他改变（原页 5b-56）

- Checksum: removed entirely to reduce processing time at each hop —— 校验和：完全取消，以减少每一跳的处理时间。其直接后果是 IPv6 基本首部中没有首部校验和字段；由于没有该字段，沿途路由器也不需在修改 hop limit 后重算校验和，这与 5.6.8 节例题中 IPv4 转发必须重算首部校验和形成对照。传输层的校验（TCP/UDP 校验和）仍然存在，端到端的差错检测由传输层承担。
- Options: allowed, but outside of header, indicated by "Next Header" field —— 选项：仍被允许，但被放在首部之外，由 "Next Header" 字段指出。
- ICMPv6: new version of ICMP —— ICMPv6：ICMP 的新版本。
  - additional message types, e.g. "Packet Too Big" —— 增加了新的报文类型，例如 "Packet Too Big"（分组过大）。
  - multicast group management functions —— 具备组播组成员管理功能。

其中 "Packet Too Big" 报文与路径 MTU 发现直接相关：IPv6 路由器遇到超过出接口 MTU 的数据报且不能分片时，用该报文通知源端，源端据此减小数据报长度。组播组管理功能在 IPv6 中并入 ICMPv6，这是相对 IPv4 版本 ICMP 的一项功能扩展。

#### IPv6 地址类型与表示法（原页 5b-57）

- Three types: unicast, multicast, anycast —— 三种类型：单播（unicast）、组播（multicast）、任播（anycast）。
- Colon hexadecimal notation: 68E6:8C64:FFFF:FFFF:0:1180:960A:FFFF —— 冒号十六进制记法。
- Zero compression（零压缩），四个等价写法示例：
  - FF05:0:0:0:0:0:0:B3 == FF05::B3
  - 0:0:0:0:0:0:128.10.2.1 == ::128.10.2.1
  - 12AB:0000:0000:CD30:0000:0000:0000:0000/60 == 12AB::CD30:0:0:0:0/60 == 12AB:0:0:CD30::/60

**冒号十六进制记法**：IPv6 地址为 128 位，写作 8 组、每组 4 位十六进制数，组间用冒号分隔，每组代表 16 位，$8\times16=128$ 位。示例 `68E6:8C64:FFFF:FFFF:0:1180:960A:FFFF` 中第 5 组写作单独的 `0`，这是合法的（每位十六进制数可不补前导零，全零组可写作 0），该示例并未使用零压缩。

**零压缩规则**：一组连续的全零组可以用双冒号 `::` 代替，但一个地址中双冒号只能出现一次（否则无法确定各自代表多少组零）。对四个示例逐一展开：

1. `FF05:0:0:0:0:0:0:B3 == FF05::B3`。原地址共 8 组：FF05、0、0、0、0、0、0、B3，其中第 2 至第 7 组共 6 组为全零，压缩后写作 FF05::B3，`::` 代表了这 6 组零。
2. `0:0:0:0:0:0:128.10.2.1 == ::128.10.2.1`。原地址前 6 组为全零，最后一组写作点分十进制 IPv4 形式的 128.10.2.1（这种写法用于表示嵌入 IPv4 地址的 IPv6 地址，即低 32 位按 IPv4 记法给出）。压缩后前 6 组零由 `::` 表示，代表 6 组零共 96 位，加上低 32 位共 128 位。
3. `12AB:0000:0000:CD30:0000:0000:0000:0000/60 == 12AB::CD30:0:0:0:0/60`。原地址 8 组为 12AB、0000、0000、CD30、0000、0000、0000、0000。第 2、3 两组连续为零，压缩为 `::`；后面的四组零按不压缩形式写作 `0:0:0:0` 保留。此写法中 `::` 代表 2 组零。斜杠后的 /60 是前缀长度，表示前 60 位为网络前缀。
4. `12AB:0:0:CD30::/60`。把第 3 个示例中 `CD30` 之后的四组零改用 `::` 表示，而把 CD30 之前的零写作 `0:0`，得到 `12AB:0:0:CD30::/60`。两式展开后均为 12AB、0、0、CD30、0、0、0、0 共 8 组，因此等价；此处 `::` 代表末尾 4 组零。

第 3、4 两组写法之所以都合法且等价，是因为该地址中存在两段连续零组（CD30 之前 2 组、CD30 之后 4 组），任一段用 `::` 表示都可，只要保证双冒号只出现一次且展开后总组数为 8。

三种地址类型的区别：unicast 标识单个接口；multicast 标识一组接口，报文交付给该组所有接口；anycast 标识一组接口，报文交付给其中按路由度量最优的一个接口（即"route to 'best' of several replicated servers"）。单播地址的结构在后续展开，组播与任播地址的结构未给出。

#### 单播地址的三级结构（原页 5b-58）

| 位区间 | 字段名 | 宽度 | 级别标注 |
|---|---|---|---|
| bit 0 ～ 47 | Global routing prefix（全局路由前缀） | 48 bit | First level（第一级） |
| bit 48 ～ 63 | Subnet ID（子网 ID） | 16 bit | Second level（第二级） |
| bit 64 ～ 127 | Interface ID（接口 ID） | 64 bit | Third level（第三级） |

横轴刻度标出 bit 0、48、64、127 四个位置，用于确定各字段的起止。三段宽度之和为 $48+16+64=128$ 位，与 IPv6 地址长度一致。三级的含义对应路由的层次：全局路由前缀用于在全球范围内把报文送到某个机构或站点的网络；子网 ID 用于在该站点内部区分不同的子网；接口 ID 用于在同一个子网内标识具体接口。这种划分使路由器可以按前 64 位（前缀 48 位 + 子网 16 位）做路由决策，而把后 64 位留给接口标识，不再参与网络前缀的划分。

#### 由 IEEE 802 地址生成 EUI-64 接口标识（原页 5b-59、5b-60）

**构造规则**：IEEE 802 地址（即通常所说的 MAC 地址）共 48 位，位刻度标出 bit 0、8、24、47 四个位置：bit 0～7 为一个字节，按位从左到右写作 `cccccc0g`（c 表示保持不变的原比特，`0` 与 `g` 分别标注为 U/L bit 与 I/G bit）；bit 8～23 共 16 位写作 `cccccccccccccccc`；bit 24～47 为 24 位，标为 "low 24 bit"。

接口 ID 共 64 位，位刻度标出 bit 0、8、24、40、63，由三部分拼成：bit 0～7 写作 `cccccc1g`；bit 8～23 写作 `cccccccccccccccc`；bit 24～39 是一个 16 位全 1 的字段，标注为 `0xFFFE`；bit 40～63 为 "low 24 bit"，与上方 802 地址的低 24 位相同。

两个字节级标签需要说明：标 "U/L bit" 的注释指向 802 地址首字节中从左数第 7 个位置的那个 `0`（自左向右索引为 6）。在把字节按高位在左、低位在右书写时，该位置对应首字节的 bit 1（数值 0x02）。标 "I/G bit" 的注释指向同一字节中从左数第 8 个位置的那个 `g`（索引为 7），对应首字节的 bit 0（数值 0x01）。接口 ID 的 `cccccc1g` 中，与 U/L bit 对应的位置由 `0` 变为 `1`，并标注 "U/L = 1"，即把 802 地址首字节的 U/L 比特置 1 就得到接口 ID 的首字节。

由此得到由 802 地址生成 64 位接口 ID 的三个动作：

1. 取 802 地址的前 24 位（首 3 字节）。
2. 在其后插入固定的 16 位值 0xFFFE（即两个字节 FF、FE）。
3. 再拼上 802 地址的后 24 位（末 3 字节）。

结果共 $24+16+24=64$ 位。此外还需把首字节的 U/L 比特由 0 置为 1。这两步合起来就是 EUI-64（Extended Unique Identifier，64 位扩展唯一标识符）接口标识的生成方法。

**实例**：

```
Example:
host MAC address:   00:0C:85:AB:50:01
insert FFFE:
00:0C:85:FF:FE:AB:50:01
set G/L bit:
02:0C:85:FF:FE:AB:50:01
host EUI-64 is:
020C:85FF:FEAB:5001
router advertise the 64bit network
prefix
Host unicast address: prefix+EUI-64
```

**逐步计算**：

第 1 步：写出主机 MAC 地址。`00:0C:85:AB:50:01`，共 6 个字节，前 3 字节为 00、0C、85，后 3 字节为 AB、50、01。

第 2 步：在中间插入 FFFE。把 00、0C、85 与 AB、50、01 之间插入两个字节 FF、FE，得到 `00:0C:85:FF:FE:AB:50:01`，共 8 个字节 = 64 位。这一步只是插入，不改动原有比特。

第 3 步：置 G/L 比特（课件此处用 "set G/L bit"，与 "U/L bit" 指同一个比特，即首字节的 bit 1、数值 0x02）。首字节原为 $0\text{x}00=00000000_2$，把 bit 1 置 1 后为 $00000010_2=0\text{x}02$。其余字节不变，得到 `02:0C:85:FF:FE:AB:50:01`。

第 4 步：按冒号十六进制记法整理。把 8 个字节两两合成 4 组、每组 16 位：02、0C → 020C；85、FF → 85FF；FE、AB → FEAB；50、01 → 5001。得到主机 EUI-64 接口标识为 **020C:85FF:FEAB:5001**。

第 5 步：组成完整单播地址。路由器通告 64 位的网络前缀（router advertise the 64bit network prefix），主机的单播地址等于该前缀与 EUI-64 拼接（Host unicast address: prefix+EUI-64）。即单播地址 = 全局路由前缀（48 位）+ 子网 ID（16 位）= 64 位网络前缀，后接上述 64 位接口标识，合计 128 位。

**校验**（用原始数据核对）：EUI-64 的高 24 位应等于 MAC 的前 24 位（00:0C:85），计算结果 020C:85… 中，去掉被置位的首字节 U/L 比特后为 00:0C:85，与原始 MAC 前 3 字节一致；EUI-64 的 bit 24～39 应为 0xFFFE，计算结果的第 4、5 字节为 FF、FE，一致；EUI-64 的低 24 位应等于 MAC 的后 24 位（AB:50:01），计算结果的末 3 字节为 AB、50、01，一致；首字节由 00 变为 02，恰好是 U/L 比特（0x02）被置 1，与 "U/L = 1" 的标注一致。四项校验全部通过。

**答案**：主机 MAC 地址为 00:0C:85:AB:50:01 时，其 EUI-64 接口标识为 **020C:85FF:FEAB:5001**；该主机的单播地址由路由器通告的 64 位网络前缀与上述 EUI-64 拼接而成。

### 5.6.11 从 IPv4 到 IPv6 的过渡与部署（原页 5b-61 至 5b-65）

#### 混合网络环境与两种过渡方案（原页 5b-61）

过渡过程中的现实约束：

- **并非所有路由器都能被同时升级（Not all routers can be upgraded simultaneous）**。互联网络由大量独立管理的自治系统与设备组成，升级需要各管理域的配合，因此**不存在统一的"切换日"（no "flag days"）**。"flag day"指约定某一天全网同时把旧协议替换为新协议的做法；课件明确否定这种可能。
- 由此产生的问题：**当网络中同时存在 IPv4 路由器和 IPv6 路由器时，网络如何运行（How will the network operate with mixed IPv4 and IPv6 routers?）**。

课件给出两种被提出的方法（Two proposed approaches）：

1. **双栈（Dual Stack）**：部分路由器同时装有 IPv6 和 IPv4 两套协议栈（dual stack，v6、v4），这类路由器可以在两种格式之间做"转换（translate）"。
2. **隧道技术（Tunneling）**：把 IPv6 分组作为**载荷（payload）**装入 IPv4 数据报中，在若干 IPv4 路由器之间传送。

两者的区别在于：双栈依赖路由器自身同时理解两种协议并按目的地址选择版本；隧道技术则让 IPv4 路由器完全不解析内层 IPv6 内容，只按外层 IPv4 首部转发，用于跨越中间一段纯 IPv4 的区域。

> **补充说明（非课件原文）**：课件在双栈条目中使用 "translate" 一词并加了引号，其含义是双栈路由器在转发时按下一跳可达的版本决定发送 v4 还是 v6 分组，并非对分组内容做协议翻译；真正意义上把一种协议首部转换为另一种的机制是 NAT 类方案，本讲不展开。

#### 双栈方法（Dual Stack Approach，原页 5b-62）

双栈下的端到端路径由 6 台设备（路由器）$A$、$B$、$C$、$D$、$E$、$F$ 串接而成，各设备对外表现出的协议版本为：

| 位置 | 设备 | 协议版本 |
|------|------|----------|
| 1 | $A$ | IPv6 |
| 2 | $B$ | IPv6 |
| 3 | $C$ | IPv4 |
| 4 | $D$ | IPv4 |
| 5 | $E$ | IPv6 |
| 6 | $F$ | IPv6 |

在这种拓扑下，路径被分为三段：$A$ 到 $B$ 为 IPv6 段，中间的 $B\to C$ 与 $D\to E$ 为 IPv4 段，$E$ 到 $F$ 为 IPv6 段。每条链路上实际传送的分组首部字段为：

| 链路 | 协议版本 | 分组首部显示的内容 |
|------|----------|--------------------|
| $A\to B$ | IPv6 | Flow: X；Source: A；Dest: F；data |
| $B\to C$ | IPv4 | Source: A；Dest: F；data |
| $D\to E$ | IPv4 | Source: A；Dest: F；data |
| $E\to F$ | IPv6 | Flow: ？？；Source: A；Dest: F；data |

从此图可以读出双栈运行的三条事实：

1. **端到端的源与目的地址保持不变**。四条链路的分组中 Source 始终为 $A$，Dest 始终为 $F$，说明版本切换不改变端到端身份，只改变承载的协议格式。
2. **源和目的之间各段可以采用不同版本**。$A\to B$ 用 IPv6，中间 $B\to C$、$D\to E$ 用 IPv4，末段 $E\to F$ 又回到 IPv6；每台路由器按其与下一跳共同支持的版本封装，因此**同一路径上版本可以交替出现**。
3. **跨越 IPv4 段时 IPv6 特有的字段信息发生变化**。$A\to B$ 的 IPv6 分组带有 Flow 标签 "X"，到 $B\to C$ 的 IPv4 分组中该字段不再出现；到达 $E\to F$ 重新成为 IPv6 分组时，图中 Flow 字段标为 "？？"，表示**经过 IPv4 段后流标签信息不能被可靠保留**。这与 IPv4 首部没有对应的 Flow Label 字段直接相关：IPv4 只能承载源、目的、数据等共有信息。

> **补充说明（非课件原文）**：双栈的含义是设备同时实现 IPv4 和 IPv6，两种协议可分别运行。课件图中另外画出了 IPv6→IPv4→IPv6 的转换过程，应将它理解为课件的过渡转换示意；普通双栈路由器不会仅因下一跳只支持 IPv4 就自动把 IPv6 数据报转换成 IPv4。跨协议版本转换还需要明确的转换机制，IPv6-over-IPv4 隧道则采用下一小节所述的外层封装，二者不可混同。

#### 隧道技术（Tunneling，原页 5b-63、5b-64）

**逻辑视图与物理视图**。同一设备序列 $A$、$B$、$C$、$D$、$E$、$F$ 的两种视图为：

| 视图 | 各设备标注的协议版本 | 链路画法 |
|------|----------------------|----------|
| logical view（逻辑视图） | $A$ IPv6；$B$ IPv6；$E$ IPv6；$F$ IPv6 | $B$ 与 $E$ 之间为一条直连链路，标注 "IPv4 tunnel connecting IPv6 routers"（连接 IPv6 路由器的 IPv4 隧道） |
| physical view（物理视图） | $A$ IPv6；$B$ IPv6；$C$ IPv4；$D$ IPv4；$E$ IPv6；$F$ IPv6 | $B$—$C$—$D$—$E$ 逐跳实连，$C$、$D$ 为 IPv4 路由器 |

由两视图的差异可知：

- **物理上**，$B$ 到 $E$ 之间并不存在一条直连链路，实际经过的是仅运行 IPv4 的路由器 $C$ 和 $D$。
- **逻辑上**，$B$ 与 $E$ 同样是 IPv6 路由器，它们之间被当作一条直接的 IPv6 通路来使用，这条通路被称为 **IPv4 隧道（IPv4 tunnel）**。
- 隧道两端的 $B$ 与 $E$ 是隧道端点（tunnel endpoint）；隧道内部的 $C$、$D$ 不需要支持 IPv6，也不需要理解内层分组的内容。

**隧道中的分组封装与各段首部**。四段的实际分组内容为：

| 链路 | 标注 | 分组实际内容 |
|------|------|--------------|
| $A\to B$ | IPv6 | flow: X；src: A；dest: F；data |
| $B\to C$ | IPv6 inside IPv4 | 外层：src: B；dest: E；内层：Flow: X；Src: A；Dest: F；data |
| $D\to E$ | IPv6 inside IPv4 | 外层：src: B；dest: E；内层：Flow: X；Src: A；Dest: F；data |
| $E\to F$ | IPv6 | flow: X；src: A；dest: F；data |

（$B\to C$ 与 $D\to E$ 两段同属隧道内部，内容相同。）由此可以读出隧道技术的四个要点：

1. **内层分组保持端到端不变**。隧道内部的内层分组仍为 `Flow: X, Src: A, Dest: F, data`，与 $A\to B$ 段的 IPv6 分组完全一致。$C$、$D$ 转发时按外层 IPv4 首部处理，内层内容不被修改。
2. **外层首部是隧道端点之间的 IPv4 首部**。外层 `src: B`、`dest: E`，即外层地址是**隧道入口与隧道出口的地址**，而不是最终目的地址 $F$。这意味着对 $C$、$D$ 而言，这个分组只是从 $B$ 发往 $E$ 的普通 IPv4 数据报。
3. **Flow 标签在隧道内被完整保留**。$A\to B$ 段 Flow 为 X，隧道内层 Flow 仍为 X，$E\to F$ 段 Flow 仍为 X。原因在于内层是完整的 IPv6 分组，其首部（含 Flow Label 字段）被原样封装，未被解析；这与双栈方案中 IPv4 段无法保留流标签（$E\to F$ 的 Flow 标为"？？"）形成对照。
4. **隧道端点的出入过程**。$B$ 收到 $A$ 发来的 IPv6 分组后，在其前面添加一个以 $E$ 为目的的 IPv4 首部并发出；$E$ 收到该 IPv4 数据报后剥去外层 IPv4 首部，恢复出原始 IPv6 分组再发给 $F$。整个过程对 $A$ 与 $F$ 均不可见，因此逻辑视图上 $B$ 与 $E$ 表现为直接相邻。

> **补充说明（非课件原文）**：隧道技术之所以必要，是因为 $C$、$D$ 只能处理 IPv4。若要求它们转发 IPv6 分组，就必须整体升级，这正是"不存在 flag day"所要避免的情形。隧道以"外层 IPv4 承载内层 IPv6"的方式绕开了对中间路由器协议版本的要求。

#### IPv6 的部署现状（原页 5b-65）

- **Google：8% 的客户端通过 IPv6 访问服务**（Google: 8% of clients access services via IPv6）。该比例以 Google 自身统计的客户端访问数据为基础。
- **NIST：美国全部政府域名中有 1/3 具备 IPv6 能力**（NIST: 1/3 of all US government domains are IPv6 capable）。1/3 指"具备 IPv6 能力"的域名比例，不等同于已实际使用 IPv6 通信的流量比例。
